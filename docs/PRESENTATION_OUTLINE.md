## ЧАСТЬ I. ПРОБЛЕМА И ЦЕННОСТЬ (для бизнеса)

### 1. Проблема и контекст
- **Цель:** объяснить, зачем система существует.
- Тезисы:
  - Разрозненные процессы: учёт кабин/бытовок, аренда, ремонт, инвентаризация, логистика, персонал.
  - Боль ручного учёта: потерянными объектами нельзя управлять, нет единой истории по каждой единице.
  - Нет единой точки правды для склада → ошибки, простои, споры по возвратам.
- Визуализация: «до/после», карта болей.

### 2. Решение одним предложением + ключевые выгоды
- **Цель:** elevator pitch.
- Тезисы:
  - RWMS объединяет идентичность складов и доступ, кабины и оборудование, операционные очереди,
    ремонт, инвентаризацию, логистику, медиа, аналитику и AI-ассистента в одной платформе.
  - Выгоды: прозрачность жизненного цикла каждой бытовки, мобильные роли (менеджер/работник/водитель),
    контроль сохранности, KPI и досье активности.
- Материалы: `README.ru.md` (вступление), `docs/project-knowledge/domain-logic.md`.

### 3. Роли и клиенты (кто и как работает)
- **Цель:** показать экосистему пользователей.
- Тезисы:
  - Web-панель (`panel/`) — менеджеры и операции.
  - Android: менеджер (`app/`), работник (`worker-app/` — назначения, стропалька, фотофиксация),
    водитель (`driver-app/` — складские задания, надёжное восстановление загрузок).
  - Клиент-приложение (`client-app/`) — клиентский сценарий аренды.
  - Распространение APK через неизменяемые download-site'ы.
- Визуализация: скриншоты клиентов, схема «роль → приложение → сценарий».

## ЧАСТЬ III. ТЕХНИЧЕСКАЯ АРХИТЕКТУРА (для технической аудитории)

### 7. Архитектура high-level
- **Цель:** одна понятная схема всей платформы.
- Тезисы (из `docs/project-knowledge/architecture.md`):
  - Клиенты → stateless API gateway → auth + публичные domain APIs.
  - Каждый stateful-сервис владеет своей PostgreSQL (Flyway-история).
  - Transactional outbox → Kafka → потребители и read-проекции.
  - media-service: приватный MinIO + производные.
- Визуализация: готовая картинка `docs/project-knowledge/rwms-microservices-architecture.png`
  или mermaid flowchart из README.

### 8. Ключевые архитектурные принципы и решения
- **Цель:** обосновать выбор микросервисов и защитить от вопросов «почему так сложно».
- Тезисы (из `README.ru.md`, раздел «Почему система разделена именно так»):
  - Ровно один владелец у каждого бизнес-инварианта и статуса.
  - Междоменные связи — только версионированные HTTP/event-контракты (`contracts/openapi`, `contracts/events`),
    никаких общих таблиц.
  - Gateway — транспортно-security граница, НЕ скрытый оркестратор.
  - Никакого межсервисного 2PC; саги хранит инициирующий домен; Kafka — не БД.
  - SSE = transport/invalidation-сигналы; оптимистичная конкурентность, fencing, idempotency.
- Визуализация: схема пути запроса (1→6 из README «Как проходят запросы и факты»).

### 9. Технологический стек
- Backend: Java / Spring Boot + Spring Cloud Stream, Gradle (каталог утверждённых версий), Flyway.
- Media: Go.
- Данные: PostgreSQL (по БД на сервис), Kafka, MinIO.
- Frontend: React 19 + TypeScript + Vite (панель), Vitest, ESLint/Prettier.
- Mobile: Android (Kotlin/Jetpack Compose — проверить в `*/build.gradle.kts`).
- Инфраструктура локальной разработки: Docker Compose (dev-зависимости), Nginx.

### 10. Безопасность и надёжность
- **Цель:** снять главные возражения заказчиков.
- Тезисы:
  - OIDC Authorization Code + PKCE, JWT edge-политика, повторная проверка токена каждым сервисом.
  - Складская изоляция и доменная авторизация на каждом ресурсе.
  - CSRF-контроль регистрации, fixed-window бюджеты регистрации в auth, канонизация X-Forwarded-For.
  - Ротация секретов с revision-fencing; dev-креды невозможны в production.
  - Outbox/inbox с дедупликацией, гарантиями порядка и версий агрегата.
- Материалы: `AGENTS.md` (правила безопасного изменения), `architecture.md`.

### 11. Контроль качества и инженерная культура
- **Цель:** показать зрелость процесса разработки.
- Тезисы:
  - Policy gates: `verifyApprovedDependencyVersions`, `verifyCanonicalContracts`, architecture-tests.
  - Канонические контракты как источник истины + compatibility-проверки producers/consumers.
  - Регулярные аудиты с доказательствами: `docs/reviews/20260808-full-architecture-audit.md`,
    декомпозиция god-классов.
  - Поддерживаемая база знаний: `docs/project-knowledge/` (change-log, open-questions).
