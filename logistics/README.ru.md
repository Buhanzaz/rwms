# Симулятор логистики RWMS

[English version](README.md)

Отдельный внутренний стенд для проектирования, планирования и воспроизведения
рабочего дня доставки и вывоза бытовок. Он остаётся отдельным deployable со
своими данными, но через явно включаемую OAuth-защищённую границу может
автоматически обновлять заказы из активного RWMS `logistics-service` и
применять точный финальный план при закрытии приёма заявок. Низкоуровневые
операции sync/apply остаются recovery API; в обычном потоке логиста нет ручного
действия обмена с RWMS. Внутри стенда нет клиентского заказа, биллинга, GPS-трекинга,
интеграций с 1С или Bitrix.

По умолчанию стенд использует приватный Valhalla 3.8.3 на данных OpenStreetMap
и всегда запрашивает `costing=truck`. Каждый дорожный участок рассчитывается
для машины, присоединённого прицепа и груза, который остаётся именно на этом
участке. Тихого fallback на легковой маршрут нет. API-ключ не нужен; интернет
нужен только для загрузки выгрузок Центрального и Северо-Западного ФО и
необязательного стиля карты. Манифест источников перестраивает производные
admin, routing tiles и tile extract при изменении любого PBF.
Если стиль MapLibre недоступен, редактор переходит на координатную сетку, а
рисование зон и симуляция сохранённых маршрутов продолжают работать.
Карта общая для всех активных канонических складов RWMS с принадлежащей owner
парой координат. Directory reconciliation создаёт или обновляет planner-
проекцию под тем же UUID; отдельного подключения и обязательного первого
полигона нет. Особая зона принадлежит ровно одному складу, поэтому отображаются
зоны только выбранного склада. Выбор склада или нажатие его маркера переключает
зоны, ресурсы, работу и планы, но не меняет viewport. Явная кнопка в header
центрирует карту по запросу, поэтому несколько маркеров можно сравнивать без
принудительного zoom. Склад без координат остаётся видимым в RWMS, но явно не
готов к маршрутизации.
Слои **Изохроны склада** и **Изохроны задания** по умолчанию выключены.
Первый после включения запрашивает фиксированные truck-контуры 60, 120, 180 и
240 минут для всех подключённых складов; второй — только для явно выбранной
заявки либо точки проверки слота. При выключенном переключателе соответствующие
контуры не запрашиваются и не рисуются. Совпавшие координаты запрашиваются один
раз с приоритетом склада. Браузер держит одновременно не более четырёх
contour-запросов, при одной ошибке отменяет оставшиеся соседние запросы и рисует
все контуры под рабочими линиями маршрута. Принадлежащий Compose
[`valhalla/rwms-entrypoint.sh`](valhalla/rwms-entrypoint.sh) сохраняет
сгенерированную конфигурацию Valhalla, но повышает её предел изохрон со
стандартных 120 до требуемых 240 минут; запуск завершается ошибкой, если лимит
не применился. Эти GeoJSON-полигоны — наглядная оценка, которая никогда не
заменяет точные участки маршрута. Отдельно импортированное бронирование
CustomerApp хранит положительную информационную полосу `travelZoneHours` от
исходного склада. Она никогда не участвует в допустимости или ранжировании, а
допустимость следующей доставки определяют точные направленные участки от
предыдущей точки доставки каждого водителя. Проверка слота возвращает точные
маршруты дня до/после и кандидатов вывоза, но не рассчитывает и не возвращает
полигоны изохрон/пересечения. Ошибка включённого contour-слоя показывается рядом
с переключателями, не создаёт синтетические круги и не меняет сохранённый спрос.

## Интерфейс

```text
┌ выбор склада / дата / закрыть приём / проверить слот / проверить / режим ┐
├───────────────┬─────────────────────────────────────┬─────────────────────┤
│ склад         │       MapLibre или карта-сетка      │ выбранный объект    │
│ особые зоны   │                                     │ форма / предупрежд. │
│ доставки      │ контуры · доставки/вывозы · маршруты│ метрики маршрута    │
│ проверка слота│                                     │ объяснение         │
│ водители      │                                     │                     │
│ машины        │                                     │                     │
│ смены         │                                     │                     │
│ доставки      │                                     │                     │
│ маршруты      │                                     │                     │
│ нераспредел.  │                                     │                     │
│ настройки     │                                     │                     │
├───────────────┴─────────────────────────────────────┴─────────────────────┤
│ симуляция: начало · назад · play/pause · вперёд · конец · скорость · время│
└───────────────────────────────────────────────────────────────────────────┘
```

Дата выбирается через общий русскоязычный React-календарь; отдельных кнопок
«Сегодня» и «Завтра» нет. Одна icon-кнопка в header меняет солнце на луну вместе
со светлой/тёмной темой RWMS. В рабочей области нет footer с
provider/map mode и нет ручных кнопок **Сохранить план** или **Обмен с RWMS**.
Явной границей финализации служит **Закрыть приём доставок**; обычные refresh и
предпланирование выполняются автоматически.

Поддерживаемый поток выбирает автоматически сверенный канонический склад RWMS,
создаёт складские ресурсы, доставки и вывозы, проверяет динамические слоты,
автоматически поддерживает предплан,
финализирует его закрытием приёма, валидирует ручные изменения и воспроизводит
положение машин. Городских fixture-рабочих областей, клонирования рабочих
областей и их импорта/экспорта JSON больше нет.

Детерминированный генератор нагрузки остаётся test/development API, но inspector
склада не показывает действий **Тест на 3 дня**, **Подключить склад** и
**Обновить из WMS**. Обычное обновление склада и заказов RWMS выполняется
автоматически. Экран заявок и
маркеры карты фильтруются общей датой планирования. Пока логист не выбрал одну
дату, заявка видна на всех согласованных клиентом датах; после назначения —
только на выбранной. Нажатие маркера открывает привязанный над этой точкой
MapLibre popup с адресом, объёмом, зоной, окнами, выбором даты и текущим
назначением водителя/цикла. До утверждения выбор другого цикла удаляет задачу из
прежнего и переносит её под тем же backend-fence версии и валидации маршрута.
Новую дату можно добавить только явным действием
после договорённости с клиентом, а назначение можно снять. Исходные допустимые
даты при этом сохраняются. Для наглядной проверки возвратов установлен более
широкий лимит крюка можно изменить в настройках выбранного склада.

Раздел **Доставки** — это диспетчерская подготовка дня. При переключении даты на
нём видны только доставки и вывозы, доступные на этот день. Для каждой позиции
со статусом READY логист обязан задать положительный интервал обслуживания либо
мягкий вариант **В течение дня** и явно отметить, проедет ли к адресу машина с
прицепом; пока хотя бы одного решения нет, построение завершается
`PLANNING_INPUT_INCOMPLETE`. Вариант на весь день намеренно не сохраняет
выдуманные границы времени и позволяет планировщику поставить точку в любое
место складского дня. Ответ «прицеп не проедет» разбивает доставку или вывоз на
транспортные части по одной бытовке и исключает её из любого цикла с
присоединённым прицепом. Ответ «проедет» разрешает автопоезд на адресе, но
никогда не отменяет ограничения безопасного truck-route Valhalla/OSM. Здесь же
задаются флаги обязательной доставки/вывоза и можно создать единичные подзадачи.
Если черновой план уже существует, изменение этих
условий помечает его устаревшим и показывает перед полем даты кнопку **Обновить
маршруты**. Перестройка сохраняет стабильные UUID циклов и допустимый ручной
порядок задач; ставший физически или по времени недопустимым порядок
отклоняется, а не переставляется скрытно. **План дня** содержит только получившийся план,
метрики, утверждение и доступное до утверждения действие **Отменить изменения**.
Перетаскивание между рейсами проверяется backend целиком и сохраняется с
контролем версии.
У правого инспектора есть доступный разделитель перетаскивания: панель можно
растянуть до половины экрана, а формы и метрики адаптируются к её ширине. Блок
технической диагностики отдельных грузовых участков из интерфейса удалён.
Кнопки header, поле даты и три равных сегмента режимов имеют одну высоту.
Действия склада размещены в двух строках по три кнопки одинаковой ширины;
при минимальной ширине инспектора их подписи аккуратно переносятся.

Режим **Проверить новый заказ** показывает после debounce подсказки адресов как
в навигаторе. Выбор подсказки разрешает канонический адрес и координаты; точка
на карте запускает обратное геокодирование и заполняет адрес, если провайдер его
знает. Если результата нет, ручной текст адреса остаётся доступен. Режим
вызывает `POST /api/planning/slot-availability` только для полной точки.
Количество бытовок принимает любое
положительное целое; вместимость объекта остаётся явным выбором `1|2`. Для
каждого из трёх клиентских окон backend проверяет вставку в существующую ходку,
отдельную ходку между существующими и каждого совместимого водителя, затем
пересчитывает весь день до складской выгрузки/загрузки и финального завершения.
Вывозы перебираются только на обратном пути и откладываются, если угрожают
любой доставке. Панель показывает структурированные причины, прибытие, крюк,
запас, число кандидатов, временную шкалу, изменение загрузки, маршруты до/после
и кандидатов вывоза. Необязательные наглядные изохроны принадлежат глобальным
переключателям карты. `POST /api/planning/slot-holds` по умолчанию удерживает один
версионированный результат десять минут; подтверждение повторно проверяет
версии источника/плана дня и атомарно повышает версию. Совпавшая зона добавляет
только отображаемую цену доставки.

Слои маршрута до/после охватывают весь затронутый день водителя. Источником
истины остаётся точная направленная симуляция расписания. Маркеры вывозов
показывают состояния `SELECTED`, `DEFERRED` и `CANDIDATE` из победившего плана.

Подтверждение валидного плана идемпотентно записывает одно **тестовое**
сообщение на каждую распределённую исходную заявку. В тексте есть дата плана,
согласованное окно, назначенное количество, время прибытия, ФИО водителя,
марка/модель и госномер машины. Паспортные данные добавляются только по явной
галочке заявки; если у назначенного водителя они не заполнены, подтверждение
отклоняется. Записи и обычная обратная связь действий по умолчанию видны
восемь секунд, затем остаются в истории колокольчика справа сверху со счётчиком
непрочитанных. Время меняется в **Настройках**, а **Очистить всё** очищает
видимую историю. Там же есть switch **Разрешить переработку** и зависимое поле
**Максимальная переработка, ч**. Этот предел расширяет точные маршруты и
публикуемую ёмкость клиентских слотов только внутри тех же календарных суток.
SMS, мессенджер или push этот MVP наружу не отправляет.

## Архитектура

Этот каталог — monorepo с изолированными runtime-контейнерами:

- `frontend/`: React, строгий TypeScript, Vite, MapLibre GL JS, Terra Draw,
  TanStack Query, Zustand, React Hook Form/Zod и dnd-kit;
- `backend/`: FastAPI, Pydantic, SQLAlchemy 2, GeoAlchemy2/Shapely и Alembic;
- `db`: PostgreSQL с PostGIS и отдельным именованным volume стенда.
- `osrm-download`: однократная загрузка обоих региональных PBF, доступных
  Valhalla read-only;
- `valhalla-init` и `valhalla`: подготовка приватных tiles и truck routing;
- `truck-restrictions-indexer`: однократный версионированный импорт Osmium
  грузовых OSM-узлов/дорог в PostGIS-индекс видимой области;
- legacy `osrm-prepare`/`osrm` доступны только через явный Compose-профиль
  `legacy-routing` и никогда не используются как truck fallback.

Nginx раздаёт production frontend и проксирует same-origin `/api` и SSE в
FastAPI. Браузер не выбирает authoritative-зону заявки. Backend хранит
складские ресурсы и версии принадлежащих им зон, планы, результаты проверки, объяснения, trace оптимизации
и аудит ручных изменений. См. [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) и
[`docs/API.md`](docs/API.md).

версионированный planning API владельца `services/logistics-service`; service
secret не попадает в браузер или form body token-запроса.

## Доменная модель

Модель хранит автоматически сверенные канонические склады RWMS и их настройки,
четыре цены изохрон и принадлежащие складам версионируемые особые зоны
Polygon/MultiPolygon с внутренними контурами, цветами и явной policy, складских водителей, машины и
месячные диапазоны смен, логистические заявки, варианты дат и отдельную
назначенную логистом дату, разбитые planning tasks, версионируемые
планы/циклы/остановки/участки, optimization runs/trace events, аудит ручных
изменений, версионированные планы дня и истекающие holds слотов. Все timestamps
имеют часовой пояс; канонический часовой пояс склада является источником истины,
а `Europe/Moscow` — только настроенный fallback. Идентичность зоны — UUID, у неё
нет бизнес-кода и приоритета; моделей связей, групп и импорта больше нет.

Координаты доставки или вывоза классифицируются backend через PostGIS только
по зонам того же склада. `FORBIDDEN` запрещает доставку, `NO_TRAILER` запрещает
маршрут с прицепом, а `SPECIAL_PRICE` переопределяет обычную цену первой
60/120/180/240-минутной полосы точного дорожного времени. Для каждой policy
побеждает покрывающая геометрия меньшей площади; при равной площади результат
детерминирован UUID зоны. Покрывающая зона складу не требуется, а точка вне
всех зон использует тариф изохроны, если truck route допустим. Изменение зоны
повышает её version и инвалидирует затронутые слоты.
Инструмент **Сделать вырез** сначала выбирает исходную незаблокированную зону,
затем создаёт строго внутренний контур и открывает форму внутренней зоны.
Сохранение одной атомарной backend-командой вырезает контур из исходной зоны и
создаёт самостоятельную особую зону версии 1 с той же геометрией. Отмена
формы не меняет ни одну зону. После любой классификации policy авторитетным
остаётся точный truck route.

## Правила логистики

- Вместимость машины по умолчанию — две бытовки, каждая остановка сохраняет
  `0 <= load <= capacity`.
- Заявка больше вместимости детерминированно разбивается, например
  `5 -> [2, 2, 1]`.
- Каждый цикл начинается и заканчивается на складе. И автоматический, и ручной
  порядок всегда держат все доставки перед всеми вывозами. Ручная вставка
  ограничивается фазой выбранной задачи, сохраняя относительный порядок
  доставок между собой и вывозов между собой; после этого всё равно проверяются
  вместимость, окна, смена, складские операции и truck-safe участки. Возврат на
  склад завершает цикл, поэтому тот же водитель может снова загрузить доставки
  в следующем независимом цикле.
- Цикл берёт одну доставку quantity=2 или пару quantity=1, затем один вывоз
  quantity=2 или пару quantity=1. Pickup-only цикл допустим со штрафом за
  пустой исходящий пробег.
- Пока приём заявок на дату открыт, сохранённый предплан уже рассматривает
  смешанные циклы и отдельные вывозные циклы. Сначала он завершает допустимые
  доставки, затем использует совместимый обратный путь и остаток смены для
  вывозов: одиночная доставка может забрать обратный груз, а отдельный дальний
  вывоз выполняется, если доставка не может занять это время. Однонаправленная
  команда **Закрыть приём заявок** сохраняет факт закрытия и пересчитывает ту же
  модель с приоритетом доставок по окончательному набору работ. Новые клиентские слоты
  на закрытую дату больше не публикуются. При включённой синхронизации с RWMS
  та же идемпотентная команда закрытия автоматически применяет распределённые
  части RWMS-доставок из точного финального плана; повторное закрытие повторяет
  применение и публикует уже зафиксированное поколение ёмкости, не строя другой
  план. Детерминированные связи склада, заказа, бытовок и водителя проверяются
  до того, как публикация ёмкости может зафиксировать ожидающее закрытие. Если
  более поздний удалённый вызов падает
  уже после локального commit снимка, браузер перечитывает авторитетное закрытое
  состояние и показывает, что внешний обмен требует повтора, а не изображает
  дату открытой.
  Уведомление нового загруженного плана также заменяет предыдущее уведомление о
  результате, поэтому оператор видит только текущие числа рейсов и
  нераспределённых задач.
- Следующий цикл того же водителя начинается не раньше возврата предыдущего
  цикла на склад плюс складская разгрузка/оборот и настроенный маршрутный
  резерв. Циклы одного водителя поэтому никогда не выполняются параллельно.
- Зоны `FORBIDDEN` отклоняют свою клиентскую точку, а `NO_TRAILER` — варианты с
  прицепом; `SPECIAL_PRICE` меняет только деньги. Каждый оставшийся кандидат
  всё равно обязан пройти точную дорожную и календарную проверку.
- `planned_arrival` клиентской точки означает фактическое начало обслуживания,
  а не ранний приезд, спрятанный внутри длинной остановки. Для первого позднего
  окна загрузка и выезд со склада сдвигаются ближе к согласованному времени.
  Для последующих окон весь уже построенный префикс рейса максимально
  сдвигается на складе, пока это не нарушает предыдущие окна. У предыдущего
  клиента может остаться только ограниченное ожидание
  (`max_customer_wait_minutes`, по умолчанию 120 минут); больший разрыв
  разделяет работу на новый цикл со склада. Valhalla заново строит участок для
  фактического отложенного времени выезда.
- При одинаковой обязательности даты планировщик предпочитает полную загрузку
  туда и обратно: `2 -> 1 -> 0 -> 1 -> 2 -> 0`. Меньшее число циклов и возвратов
  на склад имеет приоритет перед взвешенным пробегом, только пока защищены все
  доставки. Планировщик строит ограниченные контрольные планы только доставок
  в трёх порядках — по ближайшему окончанию окна, от дальних и от ближних — и
  выбирает вариант с наилучшим покрытием hard-дат, последних дат и общего
  объёма доставок; если смешанный черновик охватывает меньше, он заменяется этим
  вариантом. Затем близкий вывоз добавляется только после полной перепроверки
  всех последующих циклов этого водителя. Порог крюка 35 минут и ratio 1,5
  ограничивают только дополнительное движение по дороге; обслуживание вывоза
  по-прежнему входит в ETA, окна,
  нагрузку и проверку конца смены. Зона особой цены не может сделать дорожные
  лимиты строже. Слишком далёкий вывоз
  становится отдельным pickup-only циклом либо остаётся нераспределённым, но не
  вытесняет доставку.
- Ранжирование сначала уплотняет совместимые доставки и вывозы, затем повторно
  использует уже подключённую смену водителя/машины, пока это допустимо. Новая
  смена получает `additional_resource_activation_penalty` (по умолчанию
  эквивалент 180 минут пути) и подключается только когда этого требуют окна,
  конец смены, более плотное объединение точек или существенно лучший маршрут.
  Когда все пригодные смены уже подключены, одинаково допустимый текущий рейс
  получает смена с наименьшим остатком времени: более поздний ресурс остаётся
  свободным для работы, которую короткая смена уже не успеет завершить.
- Нагрузка водителя считается по занятому интервалу относительно длительности
  смены за вычетом настроенного перерыва. До
  `preferred_shift_utilization_percent` (по умолчанию 80%) рейсы остаются у
  уже подключённого водителя; каждая минута сверх мягкой цели получает вес
  `driver_workload_weight` (по умолчанию 3). Алгоритм сравнивает этот штраф со
  стоимостью подключения ещё одной машины. Обычный конец смены остаётся
  жёстким, пока switch переработки выключен; при включении допустим только
  настроенный максимум, он штрафуется и показывается предупреждением. То же
  ограниченное расширение публикуется в клиентскую ёмкость и не переходит через
  полночь.
- Один водитель может получить несколько циклов с возвратом на склад без
  прежнего искусственного штрафа за каждый следующий рейс.
- До включения кандидата в план backend проверяет размещение и массу груза,
  наличие прицепа и заданный оператором профиль осевой нагрузки. Первая
  бытовка ставится на машину; вторая требует совместимый прицеп и размещается
  на нём. Неполные физические данные дают `ROUTING_PROFILE_INCOMPLETE`, а
  несовместимый груз отклоняется до запроса маршрута.
- Каждый участок получает новый `EffectiveTruckProfile`. Разгрузка меняет
  фактическую массу и размещение, но не отсоединяет прицеп. Высота учитывает
  высоту платформы, ширина — самый широкий элемент техники/груза, а длина
  автопоезда берётся из точного значения либо проверенного расчёта сцепки.
  Сегмент сохраняет полный snapshot профиля, provider и версии OSM-данных.
- Ошибка Valhalla возвращается как `NO_SAFE_ROUTE`. Приложение никогда не
  повторяет запрос через `auto`, OSRM или другой легковой профиль.
- Предупреждения о мягком окне и переработке пересчитываются по финальному
  точному грузовому расписанию. Консервативная отметка матрицы удаляется, если
  построенный рейс фактически укладывается в окно и смену; реальная разрешённая
  переработка остаётся видимой.
- Ручной drag-and-drop отправляет ожидаемую версию плана и повторно проверяется
  backend. Текущий редактор переносит задачи между циклами, меняет порядок
  задач внутри цикла и блокирует целые циклы. Устаревшая операция получает
  `409 PLAN_VERSION_CONFLICT`.

Нераспределённые задачи получают стабильные reason codes и русские объяснения,
а не общее «route not found». Карточка плана показывает цепочку загрузки,
расстояние, время движения/обслуживания/ожидания/крюка, score, предупреждения и
сохранённое объяснение назначения. Карточка водителя также показывает загрузку
смены с учётом перерыва. Сводка параллельного старта показывает, сколько
действительно подключённых ресурсов должны выехать одновременно; неиспользуемые
водители и машины маршрут не получают.
Если допустимых циклов нет, интерфейс сразу открывает причины нераспределения,
а не сообщает о построенных маршрутах; симуляция недоступна, пока в плане не
появится хотя бы один цикл.

На карте отображается каждый сохранённый дорожный участок. Циклы имеют разные
цвета, при открытии плана карта охватывает весь маршрут, а легенда выбирает
целый цикл вместе с возвратом на склад. Поэтому повторяющиеся складские
сегменты не скрывают последующие плечи маршрута. Карточка **Полные маршруты**
расположена над необязательным меню слоёв, а линии маршрута рисуются выше зон,
ограничений и полигонов изохрон.

Состояние симуляции — чистая функция сохранённого плана, выбранного timestamp и
временных overrides. Поэтому перемещение времени назад воспроизводит то же
положение машины, загрузку и журнал событий. Задержка сдвигает последующие ETA,
не меняя исходный план; недоступность водителя останавливает выбранную машину и
помечает оставшиеся задачи как затронутые. Override сохраняется только при
явном `persist=true`. В режиме симуляции полный план и все карточки циклов
остаются видимыми; текущий статус водителя и popup машинки показывают адрес
назначения, ETA и загрузку. Шкала начинается с самой ранней назначенной смены,
поэтому отложенный из-за окна рейс можно прокрутить назад и увидеть машину,
ожидающую загрузки на складе.

## Запуск

Требуется Docker с Compose v2.

```bash
cd logistics
cp .env.example .env
docker compose up --build
```

Подсказки адресов как в навигаторе и обратное геокодирование для логиста
требуют отдельных серверных ключей Yandex Geosuggest и Geocoder в
`YANDEX_GEOSUGGEST_API_KEY` и `YANDEX_GEOCODER_API_KEY`. В браузер они не
передаются. Если одного из ключей нет, соответствующий endpoint явно завершается
ошибкой, а ручной ввод адреса/координат остаётся доступен; проверка слота и зон
не выдумывает ответ провайдера.

Откройте <http://localhost:5173>. Документация API находится на
<http://localhost:8000/api/docs>, схема — на
<http://localhost:8000/api/openapi.json>. Compose публикует оба development-
порта только на loopback. Valhalla остаётся приватным: Compose публикует его
порт только на `127.0.0.1`, чтобы установленный на том же VPS RWMS
logistics-service использовал ту же truck matrix без публичного routing-порта.
Первый `up` скачивает и строит обе заданные выгрузки OpenStreetMap и индексирует
их дедуплицированные грузовые ограничения, поэтому для объединённого графа
может занять десятки минут; следующие запуски используют
`logistics-osrm-data`, `logistics-valhalla-data` и пропускают уже
импортированную `OSM_DATA_VERSION`. Ключи routing/basemap не нужны; для
необязательного адресного потока используются два серверных ключа выше.

На текущем VPS стенд публикуется Nginx по
<https://77-90-158-90.sslip.io/logistics-simulator/>. Для path-based reverse
proxy build использует `VITE_APP_BASE_PATH=/logistics-simulator/` и
`VITE_API_BASE_URL=/logistics-simulator/api`; backend остаётся loopback-only.
Пространство `/logistics/**` остаётся за основной панелью RWMS и не должно
перенаправляться на отдельный симулятор или перекрываться им. Публичные
location-блоки Nginx зафиксированы в `deploy/nginx-public-path.conf`.

### Приватный мост RWMS только для VPS

Обычный Compose-файл остаётся самодостаточным для локального запуска. На VPS
отдельный overlay `docker-compose.vps.yml` подключает только `backend` к
постоянной внешней Docker-сети `rwms-logistics-private`. Один раз создайте
сеть с фиксированным gateway `172.21.0.1`, разверните
`deploy/nginx-rwms-private-bridge.conf` как конфигурацию Nginx и запускайте
Compose с обоими файлами. Nginx слушает только этот Docker gateway и проксирует
лишь `/oauth2/token` и `/api/internal/logistics/v1/planning/` к RWMS-сервисам,
привязанным к loopback.

Firewall хоста должен разрешать TCP только из `172.21.0.0/16` к этим двум
gateway-listener. Не привязывайте порты RWMS или этот мост к публичному адресу
VPS. `deploy/nginx.service.d/rwms-logistics-private-bridge.conf` запускает
Nginx после Docker, поэтому адрес постоянной сети существует и после reboot.

Полезные команды:

```bash
make up
make ps
make logs
make index-truck-restrictions
make down
```

`make reset-db` удаляет только Compose volume этого симулятора. Команда
намеренно явная, потому что удаляет все локальные данные стенда.
`make index-truck-restrictions` не меняет логистические данные и пропускает уже
импортированную версию OSM.

## Тестирование

Полный контейнерный gate:

```bash
make test
```

Он запускает backend tests, Ruff и строгий mypy, затем frontend Vitest,
строгий TypeScript, ESLint и production build. Эквивалентные локальные
backend-проверки:

```bash
cd backend
python -m venv .venv
. .venv/bin/activate
pip install -e '.[dev]'
pytest
ruff check app tests
mypy app
```

Эквивалентные локальные frontend-проверки:

```bash
cd frontend
npm ci
npm run test:run
npm run typecheck
npm run lint
npm run build
```

При запущенном Compose выполните browser smoke flow:

```bash
cd frontend
npx playwright install chromium
npm run e2e
```

После изменения backend API пересоберите проверяемую транспортную границу:

```bash
make openapi
```

## Синхронизация с RWMS

Интеграцией с RWMS управляет сервер, и она выполняется автоматически. Для её
включения создайте выделенный OAuth client `logistics-planner` в
`auth-service`, задайте переменные `RWMS_*` выше и откройте канонический
справочник складов. Каждая активная запись с координатами автоматически
сверяется под UUID RWMS; адрес остаётся display metadata, а отсутствие пары
координат даёт явное состояние маршрутизации `COORDINATES_REQUIRED`. Водители,
опорные связи представительского склада и доступность подрядчиков читаются из
private-справочников RWMS; подключать или обновлять склад вручную из панели не
требуется.
Каноническую запись только с адресом можно выбрать единственной кнопкой
добавления в верхней панели: сервер разрешает принадлежащий RWMS адрес через
существующий геокодер, сохраняет производную точку, пока адрес не изменён, и
сразу уступает координатам владельца, когда RWMS начинает их передавать.

Для представительского склада тот же планировщик проверяет локальные ресурсы,
активные оперативные назначения, каждый допустимый по календарю опорный склад и
подтверждённые смены подрядчиков. Кандидат опорного склада сохраняет свой
источник, точное дорожное прибытие и доступность после буфера. Он может выполнить
разовое межскладское обслуживание без смены базирования либо явный transfer
перемещения ресурса активирует назначение склада назначения после прибытия.
Потенциальный ресурс даёт только слот с подтверждением; гарантированное точное
окно всё равно требует выполнимого и резервируемого плана.

`GET /api/warehouses/{warehouse_id}/workspace` при включённой синхронизации
обновляет авторитетный горизонт заявок на 31 день до возврата рабочей области.
Заказы обновляются по стабильной идентичности `(warehouse, RWMS, orderId)` с
сохранением их версий и UUID бытовок. При наличии адреса и координат
авторитетны координаты; строка только с адресом завершается явной ошибкой
`COORDINATES_REQUIRED`, а не выдуманной точкой. Корректные соседние заказы
остаются сохранёнными при ошибке другой строки, но
`RWMS_WORKSPACE_SYNC_INCOMPLETE` не позволяет считать частичный результат
актуальным. Параметр `refresh_rwms=false` читает последнюю сохранённую проекцию
только для явного recovery-режима.

Создание или изменение авторитетной заявки инвалидирует планы только на
объединении её прежних и новых допустимых дат. Затем backend пересобирает
отсутствующие черновики для полностью заполненных дат; открытие даты также
идемпотентно создаёт её черновик. Ручной кнопки построения первоначального
маршрута нет; после изменения условий существующего черновика появляется
описанная выше кнопка **Обновить маршруты**.
Планирование начинается, только если у каждой допустимой READY-доставки или
вывоза есть корректное окно либо мягкий вариант на весь день, ответ о проезде с
прицепом и полный профиль груза, а дату
покрывает хотя бы одна активная смена водителя с машиной. Каждый цикл загружает
не более двух бытовок и возвращается на выбранный склад. Автоматическая
эвристика отдаёт приоритет доставкам; проверенный ручной порядок сохраняется
внутри фаз доставок и вывозов, но никогда не ставит вывоз перед доставкой.

Статус дня читается через
`GET /api/warehouses/{warehouse_id}/planning-days/{date}`. Действие **Закрыть
приём доставок** вызывает идемпотентный соответствующий endpoint `/close`,
пересчитывает этот день и при включённой синхронизации автоматически применяет
назначенные RWMS-доставки финального плана. Точная пара план/версия служит
optimistic- и idempotency-fence; устаревшая версия завершается конфликтом, а не
перезаписывает новый план. Низкоуровневые endpoints применения и статуса плана
остаются только для проверяемого recovery и диагностики и не показываются как
обычное окно обмена.

Публикация ёмкости включается отдельно и требует синхронизации. Изменения
складских ресурсов и замена сгенерированной нагрузки публикуют один
версионированный полный снимок сгенерированных доставок/вывозов, активных
периодических смен, вместимости машин и только особых зон этого склада. Каждая
зафиксированная мутация увеличивает поколение ёмкости склада, поэтому повторы
идемпотентны, а запоздалые старые поколения отклоняются. Ручные заявки и
импортированные заказы RWMS не публикуются повторно как сгенерированный спрос;
замена ёмкости никогда не удаляет реальное бронирование RWMS. `POST
/api/warehouses/{warehouse_id}/rwms/capacity` — эксплуатационный endpoint
сверки, а не кнопка панели.

Ни одна локальная транзакция БД не остаётся открытой во время OAuth или RWMS
HTTP I/O. Импорт закрывает read-транзакцию до получения feed; применение
фиксирует и сохраняет снимок точной команды до идемпотентного удалённого
вызова.

## Valhalla и грузовая маршрутизация OpenStreetMap

При `ROUTING_PROVIDER=valhalla` ограниченная Haversine-матрица служит только
предварительным фильтром комбинаций. Кандидат не считается допустимым, пока
каждый его участок отдельно не запрошен у приватного Valhalla с
`costing=truck` и собственным `EffectiveTruckProfile`. Точные distance/duration
Valhalla заново проверяют окна, конец смены и score. Сохранённые GeoJSON и
snapshot профиля используются карточками, линиями карты, диагностикой и
симуляцией. Некорректную геометрию участка или ссылку плана на отсутствующее
задание браузер отклоняет: для неполного авторитетного состояния он не
выдумывает прямую линию, нулевую координату или placeholder-задание.

Профиль содержит фактические высоту, ширину, полную длину автопоезда, полную
массу, число осей и настроенную максимальную реальную нагрузку на ось. Он
вычисляется из сохранённых машины, прицепа, платформы и размещения груза, а не
копируется из общего типа машины. Cache identity включает точки, профиль,
время отправления, версии provider и `OSM_DATA_VERSION`. Проверенная таблица
поддержки находится в
[`docs/osm-truck-restrictions.md`](docs/osm-truck-restrictions.md); неизвестные
conditional tags не выдаются в UI за безопасно учтённые.

В меню слоёв карты есть необязательный переключатель **Ограничения грузового
транспорта**. На масштабе 8 и крупнее он загружает ограниченную текущей областью
выборку PostGIS той же `OSM_DATA_VERSION`, показывает ограничения дорог
и точечные знаки с текстовыми маркерами, а по нажатию открывает теги и статус
поддержки. Частичные и неподдерживаемые теги явно помечены; слой не решает
допустимость маршрута и не заменяет truck costing Valhalla. OSM-отношения
ограничений поворота остаются логикой routing graph и не изображаются
выдуманными кликабельными линиями.

Граф не получает живой traffic feed: длительность определяется собранным OSM,
а не пробками Яндекса. Обычный runtime объединяет `OSRM_DATA_URL` и
`OSM_NORTHWESTERN_DATA_URL`; их манифест источников принудительно перестраивает
производные admin/tiles/extract Valhalla при изменении любого PBF. Вместе с
набором источников обновляйте `OSM_DATA_VERSION`, чтобы совпадали snapshots
маршрутов, cache keys и дедуплицированный индекс ограничений. Отдельный
логистический PostGIS volume при этом не удаляется. Футер рабочей области карты
выключен; deployment всё равно обязан соблюдать требования лицензии
OpenStreetMap к attribution. Приватный router нельзя публиковать наружу.

Только для legacy-разработки можно выполнить
`docker compose --profile legacy-routing up osrm`; выбранный `osrm` не является
безопасной грузовой маршрутизацией и никогда не включается автоматически.

## MockRoutingProvider

Явный тестовый провайдер не использует сеть. Он вычисляет Haversine distance,
применяет road factor выбранного склада, выбирает среднюю скорость города/области,
учитывает простой traffic multiplier по времени отправления и возвращает
distance, duration, данные участков и GeoJSON LineString. Одинаковые входы и
seed дают одинаковый результат. Ключ матричного кэша включает точки, routing
settings, временной bucket отправления и версию настроек склада.

## Настройка машины, прицепа и груза

Откройте **Машины**, создайте или измените машину и заполните раздел
**Грузовая маршрутизация**: собственную/максимальную массу, габариты, параметры
осей, геометрию платформы, ограничения груза и safety margins. В том же рабочем
месте создайте прицеп, выберите его как основной совместимый прицеп машины и
укажите либо точную длину автопоезда, либо длину сцепки для её расчёта. Затем
задайте измеренный `maxActualAxleLoadKg` для каждого используемого рабочего
состояния; приложение намеренно не делит общую массу на число осей.
Для автопоезда это максимальное измеренное значение среди всех осей машины и
прицепа, а не отдельный вектор по компонентам, поэтому пределы каждого
компонента всё равно требуют эксплуатационного замера. Поля машины и полный
набор осевых профилей сохраняются одной backend-
транзакцией, поэтому ошибка валидации не оставляет частично изменённую машину.

До сохранения форма показывает preview для одной и двух бытовок. Генератор
создаёт заявки с введёнными там габаритами груза; редактор ручной заявки
принимает такой же полный набор длины, ширины, высоты и массы. Текущий planning-
контракт RWMS эти физические поля не передаёт, поэтому для новой RWMS-доставки
без измеренного профиля стенд применяет явно заданные в настройках склада
стандартные габариты. Начальные значения — `6000 x 2400 x 2400 мм` и `1200 кг`;
администратор обязан поддерживать их в соответствии с фактической стандартной
бытовкой компании. Уже обогащённую заявку этот fallback не перезаписывает. В
готовом плане откройте
машину/цикл и разверните **Диагностику маршрута**, чтобы увидеть неизменяемый
профиль каждого участка. Старый сегмент без snapshot явно помечается
непроверенным и не может оставаться locked при повторной оптимизации Valhalla.

Интеграционный тест реального движка строит одноразовый OSM-граф с тегами и
доказывает: машина длиной 9 м выбирает короткую дорогу, а автопоезд длиной 18 м
обходит её ограничение `maxlength=12`. На том же графе проверяются высота,
ширина, полная масса, осевая нагрузка и `hgv=no`:

```bash
make test-valhalla-truck
```

## Эвристический планировщик

`HeuristicPlanner` намеренно моделирует рабочий шаблон
«доставки, затем вывозы», а не изображает универсальный VRP solver. Он:

1. проверяет смены/ресурсы на дату и разбивает готовые заявки;
2. строит детерминированную travel matrix;
3. сортирует доставки по hard/последней дате, ручному priority, дефициту дат и
   узкому окну, затем собирает равноприоритетные задания от ближних к дальним;
4. ставит каждый кандидат ко времени со склада, максимально сдвигает уже
   построенный префикс с учётом предыдущих окон и отклоняет комбинацию, если
   остаточное ожидание у клиента превышает `max_customer_wait_minutes`;
5. рассматривает ограниченное число пар доставок и оба порядка;
6. рассматривает не более `max_candidate_neighbors` групп вывозов с наименьшим
   крюком для каждой группы доставок, оставляет только группы внутри обоих
   лимитов;
7. сравнивает смешанный черновик с ограниченными контрольными планами доставок
   по ближайшему deadline, от дальних и от ближних и восстанавливает лучший,
   если упало покрытие обязательных, последних
   по дате или всех доставок, а затем добавляет вывоз только через полную
   валидную перепланировку остатка смены;
8. разрешает тому же водителю следующий загруженный на складе цикл и создаёт
   pickup-only циклы со штрафом после того, как ни одна оставшаяся доставка не
   помещается, независимо от того, открыт или закрыт приём заявок;
9. глобально назначает следующий лучший цикл свободному водителю;
10. сравнивает подключение ресурса с нагрузкой водителя с учётом перерыва;
11. выполняет ограниченные и полностью валидируемые локальные улучшения;
12. сохраняет метрики, объяснения, причины и ограниченный trace.

По достижении time/iteration limit движок предсказуемо возвращает лучший
найденный валидный план. Seed сохраняется в optimization run.

## Development API нагрузки и воспроизводимость

Для настраиваемой нагрузки выберите **Генератор заявок**. Задайте первую дату,
горизонт от одного до 31 дня, от нуля до десяти доставок и вывозов в день, до
трёх дополнительных допустимых дат и seed. Одна транзакция удаляет сохранённые
планы внутри горизонта, заменяет только созданные генератором заявки с основной
датой внутри горизонта и создаёт новый набор. Ручные и RWMS-заявки,
сгенерированная работа на другие даты и планы вне горизонта не меняются. Ошибка
маршрутизации или привязки к дороге восстанавливает прежнюю нагрузку.

Сгенерированные доставки получают жёсткие окна по кругу `09:00-12:00`,
`12:00-15:00` и `15:00-18:00`; вывозы используют рабочее окно склада. Каждая
точка начинается внутри тарифной зоны выбранного склада и при Valhalla должна
привязаться к дороге внутри этой зоны, иначе весь запуск завершается с
`422 NO_ROUTABLE_POINT_IN_ZONE`. Одинаковые геометрия складских зон, routing graph,
входные параметры и seed воспроизводят одинаковые предметные значения.
Стабильные внешние идентификаторы не позволяют повторному запуску генератора
создать дубли логических посещений.

Действие **Удалить нагрузку** удаляет созданные генератором заявки и сохранённые
планы только выбранной даты выбранного склада. Переключатель даты, список
заявок и карта показывают одну отфильтрованную работу; маркеры доставок и
вывозов открывают данные заявки. Настройки склада хранят независимые
неотрицательные цены в целых рублях для полос изохрон 60/120/180/240 минут.
Зона `SPECIAL_PRICE` имеет явное переопределение, а `FORBIDDEN` и `NO_TRAILER`
не содержат цену. Рассчитанный тариф виден в заявке и панели динамических
слотов и публикуется через существующую capacity boundary.

Mutation smoke Playwright выключен без
`RWMS_E2E_DISPOSABLE_DATABASE=true`; без этого явного разрешения browser suite
остаётся read-only.

## Ограничения MVP

Это внутренний планировочный стенд, не production dispatch system. В нём
локальный audit actor `local-admin`, нет интерактивной production
identity/access model, реального трафика/GPS, встроенного приложения водителя,
push, клиентского checkout и платежей. Опциональный machine-to-machine доступ к
RWMS ограничен отдельным planning scope. Valhalla использует закреплённую
статическую выгрузку OSM и не знает живые пробки/перекрытия без отдельного
feed. Поддерживаемые и неподдерживаемые truck-теги документированы; система не
заявляет полную поддержку произвольных conditional numeric restrictions.
Геометрия mock-маршрута остаётся прямой GeoJSON polyline только для
детерминированных тестов.

Из P1 уже реализованы сохраняемые фазы/candidate events планировщика и
симуляция недоступности водителя. За пределами текущего
MVP намеренно остаются:

- экран сравнения сохранённых планов;
- отдельный workflow рисования нового MultiPolygon несколькими контурами
  (импорт, хранение, отображение и редактирование существующих MultiPolygon
  поддерживаются);
- ручной split/merge циклов и полный remaining-day replan от
  интерполированной текущей позиции машины; текущая повторная оптимизация
  сохраняет locked-циклы и строит незаблокированную работу от склада;
- полный набор межцикловых операторов локального поиска (автоматический
  перенос/обмен циклов, замена вывоза и split/merge). Ограниченный пост-проход
  сейчас проверяет оба порядка доставок и вывозов; перенос и перестановка задач
  между циклами доступны через валидируемый backend ручной редактор;
- линии кандидатов с координатами в каждом trace event; реальные фазы и решения
  по кандидатам сохраняются, но UI рисует линию только при наличии координат в
  событии;
- внешний optimization worker с прерываемой live-отменой. Текущая ограниченная
  эвристика выполняется внутри API-процесса и возвращает terminal run, поэтому
  сохраняемый cancel flag является интеграционной границей, но не надёжно
  прерывает уже выполняющийся запрос;
- адаптер Yandex/другого traffic-aware routing, OR-Tools/CP-SAT engine,
  production-auth, сертификация high-volume benchmark и дополнительные типы
  инцидентов.

Production frontend сейчас выдаёт предупреждение Vite о крупном chunk (около
1,70 MB до gzip); route-level code splitting остаётся оптимизацией и не мешает
запуску приложения.

## Подключение другого реального routing provider

Реализуйте `RoutingProvider.get_matrix()` и `get_route()` в
`backend/app/routing`, верните существующий typed-контракт
distance/duration/legs/geometry, добавьте provider-specific config и выберите
адаптер через `ROUTING_PROVIDER`. Credentials должны оставаться на сервере;
нужны timeout/rate-limit/cache и общие provider contract tests. Будущий Yandex
adapter не должен требоваться для mock-запуска и не может заменять финальную
доменную валидацию.

## Подключение OR-Tools или CP-SAT

Реализуйте протокол `PlannerEngine.generate_plan()` в `backend/app/planner`,
преобразуйте тот же immutable planning input/settings и верните тот же
валидированный контракт cycles, explanations, metrics, reasons и progress
events. Включайте движок явной конфигурацией и сохраняйте эвристику как
детерминированный вариант без дополнительной зависимости. Результат solver не
может обходить общий валидатор hard-инвариантов.
