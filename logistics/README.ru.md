# Симулятор логистики RWMS

[English version](README.md)

Отдельный внутренний стенд для проектирования, планирования и воспроизведения
рабочего дня доставки и вывоза бытовок. Он остаётся отдельным deployable со
своими данными, но через явно включаемую OAuth-защищённую границу может
импортировать заказы из активного RWMS `logistics-service` и применять обратно
проверенный план. Внутри стенда нет клиентского заказа, биллинга, GPS-трекинга,
интеграций с 1С или Bitrix.

По умолчанию стенд использует приватный Valhalla 3.8.3 на данных OpenStreetMap
и всегда запрашивает `costing=truck`. Каждый дорожный участок рассчитывается
для машины, присоединённого прицепа и груза, который остаётся именно на этом
участке. Тихого fallback на легковой маршрут нет. API-ключ не нужен; интернет
нужен только для загрузки региональной выгрузки и необязательного стиля карты.
Если стиль MapLibre недоступен, редактор переходит на координатную сетку, а
рисование зон и симуляция сохранённых маршрутов продолжают работать.

## Интерфейс

```text
┌ сценарий / дата / построить / проверить / сохранить / режим              ┐
├───────────────┬─────────────────────────────────────┬─────────────────────┤
│ сценарий      │                                     │ выбранный объект    │
│ склад         │       MapLibre или карта-сетка      │ форма / предупрежд. │
│ зоны          │ зоны · заявки · маршруты · машины   │ метрики маршрута    │
│ связи         │                                     │ объяснение          │
│ водители      │                                     │                     │
│ машины        │                                     │                     │
│ смены         │                                     │                     │
│ заявки        │                                     │                     │
│ маршруты      │                                     │                     │
│ нераспредел.  │                                     │                     │
│ настройки     │                                     │                     │
├───────────────┴─────────────────────────────────────┴─────────────────────┤
│ симуляция: начало · назад · play/pause · вперёд · конец · скорость · время│
└───────────────────────────────────────────────────────────────────────────┘
```

Поддерживаемый поток создаёт или сбрасывает сценарий, ставит склад, рисует
зоны, управляет направленными связями, создаёт ресурсы и заявки, генерирует
план, валидирует ручные изменения и воспроизводит положение машин для любого
момента времени. Встроенное demo содержит четыре зоны, трёх водителей, три
машины вместимостью две бытовки, смены и совместимые доставки/вывозы. Для
воспроизводимости полного цикла и на mock routing, и на локальном графе Valhalla
только у demo установлен лимит крюка 60 минут и ratio 3,0: оба провайдера строят
минимальное число смешанных циклов без возврата после одних доставок. Обычные
сценарии сохраняют значения по умолчанию 35 минут и 1,5. У demo-машин также
полностью заполнены физические параметры, платформа, прицеп и эксплуатационные
осевые профили, поэтому Valhalla проверяет маршрут без выдуманных габаритов.

Действие **Тест на 3 дня** создаёт отдельную, неразрушающую нагрузку: шесть
зон, ровно три одновременно доступные машины/водителя и смены на три даты. На
каждой дате видно ровно 10 заявок: часть клиентов с первого дня согласна и на
следующий, а две заявки второго дня доступны также на третий. Экран заявок и
маркеры карты фильтруются общей датой планирования. Пока логист не выбрал одну
дату, заявка видна на всех согласованных клиентом датах; после назначения —
только на выбранной. Нажатие маркера открывает привязанный над этой точкой
MapLibre popup с адресом, объёмом, зоной, окнами и выбором даты. Новую дату можно добавить только явным действием
после договорённости с клиентом, а назначение можно снять. Исходные допустимые
даты при этом сохраняются. Для наглядной проверки возвратов установлен более
широкий лимит крюка: 60 минут и ratio 3.0; его можно изменить в настройках
сценария.

## Архитектура

Этот каталог — monorepo с изолированными runtime-контейнерами:

- `frontend/`: React, строгий TypeScript, Vite, MapLibre GL JS, Terra Draw,
  TanStack Query, Zustand, React Hook Form/Zod и dnd-kit;
- `backend/`: FastAPI, Pydantic, SQLAlchemy 2, GeoAlchemy2/Shapely и Alembic;
- `db`: PostgreSQL с PostGIS и отдельным именованным volume стенда.
- `osrm-download`: однократная загрузка PBF, доступного Valhalla read-only;
- `valhalla-init` и `valhalla`: подготовка приватных tiles и truck routing;
- `truck-restrictions-indexer`: однократный версионированный импорт Osmium
  грузовых OSM-узлов/дорог в PostGIS-индекс видимой области;
- legacy `osrm-prepare`/`osrm` доступны только через явный Compose-профиль
  `legacy-routing` и никогда не используются как truck fallback.

Nginx раздаёт production frontend и проксирует same-origin `/api` и SSE в
FastAPI. Браузер не выбирает authoritative-зону заявки. Backend хранит факты
сценария, версии зон, планы, результаты проверки, объяснения, trace оптимизации
и аудит ручных изменений. См. [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) и
[`docs/API.md`](docs/API.md).

│   └── tests/            unit, property и database integration tests

├── Makefile
├── .env.example
├── README.md
└── README.ru.md

Каталог никогда не разделяет БД или изменяемую доменную модель с deployables
активного RWMS. При выключенной синхронизации runtime-зависимости от RWMS нет.
При явном включении backend получает короткоживущий OAuth2 client-credentials
token зарегистрированным методом `client_secret_basic` и вызывает только
версионированный planning API владельца `services/logistics-service`; service
secret не попадает в браузер или form body token-запроса.

## Доменная модель

Модель хранит сценарии и настройки, склады, версионируемые зоны
Polygon/MultiPolygon с внутренними контурами, отдельными тестовыми ценами по
направлению и направленные связи, водителей, машины и смены по датам,
логистические заявки, варианты дат и отдельную
назначенную логистом дату, разбитые planning tasks, версионируемые
планы/циклы/остановки/участки, optimization runs/trace events и аудит ручных
изменений. Все timestamps имеют часовой пояс; зона сценария по умолчанию —
`Europe/Moscow`.

Координаты заявки классифицируются backend через PostGIS. Побеждает покрывающая
зона с наибольшим priority; при равном priority выбирается полигон меньшей
площади. Точка вне всех зон сохраняется как `OUTSIDE_ZONES`. Изменение зоны
повышает её version, но не переписывает молча старую принадлежность заявок.
Инструмент **Сделать вырез** сначала выбирает исходную незаблокированную зону,
затем создаёт строго внутренний контур и открывает форму внутренней зоны.
Сохранение одной атомарной backend-командой вырезает контур из исходной зоны и
создаёт самостоятельную зону версии 1 с той же геометрией. Отмена формы не
меняет ни одну зону. Пересчёт заявок остаётся явным: **Построить маршруты**
обнаруживает видимые готовые заявки без зоны или с устаревшей версией и просит
логиста подтвердить пересчёт перед запуском оптимизации.

## Правила логистики

- Вместимость машины по умолчанию — две бытовки, каждая остановка сохраняет
  `0 <= load <= capacity`.
- Заявка больше вместимости детерминированно разбивается, например
  `5 -> [2, 2, 1]`.
- Каждый цикл начинается и заканчивается на складе. Внутри этого цикла все
  загруженные на складе доставки идут раньше всех вывозов. Возврат на склад
  завершает цикл, поэтому тот же водитель может снова загрузить доставки в
  следующем независимом цикле.
- Цикл берёт одну доставку quantity=2 или пару quantity=1, затем один вывоз
  quantity=2 или пару quantity=1. Pickup-only цикл допустим со штрафом за
  пустой исходящий пробег.
- Связи зон — фильтр кандидатов, а не жёсткая география. Связь `BLOCKED` или
  отключённый переход к вывозу являются жёсткими; проверяются оба порядка
  точек, реальные окна, длина/время, конец смены и вместимость.
- При одинаковой обязательности даты планировщик предпочитает полную загрузку
  туда и обратно: `2 -> 1 -> 0 -> 1 -> 2 -> 0`. Меньшее число циклов и возвратов
  на склад имеет приоритет перед взвешенным пробегом, только пока защищены все
  доставки. Планировщик строит ограниченные контрольные планы только доставок
  в двух порядках — от дальних и от ближних — и выбирает вариант с наилучшим
  покрытием hard-дат, последних дат и общего объёма доставок; если смешанный
  черновик охватывает меньше, он заменяется этим вариантом. Затем близкий вывоз
  добавляется только после полной перепроверки всех последующих циклов этого
  водителя. Порог крюка 35 минут и ratio 1,5 ограничивают только дополнительное
  движение по дороге; обслуживание вывоза по-прежнему входит в ETA, окна,
  нагрузку и проверку конца смены. Связь зон может сделать дорожные лимиты
  строже. Слишком далёкий вывоз
  становится отдельным pickup-only циклом либо остаётся нераспределённым, но не
  вытесняет доставку.
- Группа водителя — мягкое предпочтение. Hard-даты/окна, уникальность задачи,
  пересечение водителя/машины и hard-лимит смены остаются строгими запретами.
- Ранжирование сначала уплотняет совместимые доставки и вывозы, затем повторно
  использует уже подключённую смену водителя/машины, пока это допустимо. Новая
  смена получает `additional_resource_activation_penalty` (по умолчанию
  эквивалент 180 минут пути) и подключается только когда этого требуют окна,
  конец смены, более плотное объединение точек или существенно лучший маршрут.
- Нагрузка водителя считается по занятому интервалу относительно длительности
  смены за вычетом настроенного перерыва. До
  `preferred_shift_utilization_percent` (по умолчанию 80%) рейсы остаются у
  уже подключённого водителя; каждая минута сверх мягкой цели получает вес
  `driver_workload_weight` (по умолчанию 3). Алгоритм сравнивает этот штраф со
  стоимостью подключения ещё одной машины, а фактический конец смены остаётся
  жёстким ограничением.
- Один водитель может получить несколько циклов с возвратом на склад без
  прежнего искусственного штрафа за каждый следующий рейс.
- До включения кандидата в план backend проверяет размещение и массу груза,
  наличие прицепа и заданный оператором профиль осевой нагрузки. Первая
  бытовка ставится на машину; вторая требует совместимый прицеп и размещается
  на нём. Неполные физические данные дают `ROUTING_PROFILE_INCOMPLETE`, а
  несовместимый груз отклоняется до запроса маршрута.
- Каждый участок получает новый `EffectiveTruckProfile`. Разгрузка меняет
  фактическую массу и размещение, но не отсоединяет прицеп. Высота учитывает
  высоту платформы, ширина — самый широкий элемент техники/груза, а длина
  автопоезда берётся из точного значения либо проверенного расчёта сцепки.
  Сегмент сохраняет полный snapshot профиля, provider и версии OSM-данных.
- Ошибка Valhalla возвращается как `NO_SAFE_ROUTE`. Приложение никогда не
  повторяет запрос через `auto`, OSRM или другой легковой профиль.
- Ручной drag-and-drop отправляет ожидаемую версию плана и повторно проверяется
  backend. Текущий редактор переносит задачи между циклами, меняет порядок
  задач внутри цикла и блокирует целые циклы. Устаревшая операция получает
  `409 PLAN_VERSION_CONFLICT`.

Нераспределённые задачи получают стабильные reason codes и русские объяснения,
а не общее «route not found». Карточка плана показывает цепочку загрузки,
расстояние, время движения/обслуживания/ожидания/крюка, score, предупреждения и
сохранённое объяснение назначения. Карточка водителя также показывает загрузку
смены с учётом перерыва. Сводка параллельного старта показывает, сколько
действительно подключённых ресурсов должны выехать одновременно; неиспользуемые
водители и машины маршрут не получают.
Если допустимых циклов нет, интерфейс сразу открывает причины нераспределения,
а не сообщает о построенных маршрутах; симуляция недоступна, пока в плане не
появится хотя бы один цикл.

На карте отображается каждый сохранённый дорожный участок. Циклы имеют разные
цвета, при открытии плана карта охватывает весь маршрут, а легенда выбирает
целый цикл вместе с возвратом на склад. Поэтому повторяющиеся складские
сегменты не скрывают последующие плечи маршрута.

Состояние симуляции — чистая функция сохранённого плана, выбранного timestamp и
временных overrides. Поэтому перемещение времени назад воспроизводит то же
положение машины, загрузку и журнал событий. Задержка сдвигает последующие ETA,
не меняя исходный план; недоступность водителя останавливает выбранную машину и
помечает оставшиеся задачи как затронутые. Override сохраняется только при
явном `persist=true`. В режиме симуляции полный план и все карточки циклов
остаются видимыми; текущий статус водителя и popup машинки показывают адрес
назначения, ETA и загрузку.

## Запуск

Требуется Docker с Compose v2.

```bash
cd logistics
cp .env.example .env
docker compose up --build
```

Откройте <http://localhost:5173>. Документация API находится на
<http://localhost:8000/api/docs>, схема — на
<http://localhost:8000/api/openapi.json>. Compose публикует оба development-
порта только на loopback. Valhalla доступен только внутри Compose-сети и не
имеет host-порта. Первый `up` скачивает и строит заданную выгрузку
OpenStreetMap и индексирует её грузовые ограничения, поэтому для регионального
графа может занять десятки минут; следующие запуски используют
`logistics-osrm-data`, `logistics-valhalla-data` и пропускают уже
импортированную `OSM_DATA_VERSION`. Routing/map key не нужен.

На текущем VPS стенд публикуется Nginx по
<https://77-90-158-90.sslip.io/logistics-simulator/>. Для path-based reverse
proxy build использует `VITE_APP_BASE_PATH=/logistics-simulator/` и
`VITE_API_BASE_URL=/logistics-simulator/api`; backend остаётся loopback-only.
Пространство `/logistics/**` остаётся за основной панелью RWMS и не должно
перенаправляться на отдельный симулятор или перекрываться им. Публичные
location-блоки Nginx зафиксированы в `deploy/nginx-public-path.conf`.

### Приватный мост RWMS только для VPS

Обычный Compose-файл остаётся самодостаточным для локального запуска. На VPS
отдельный overlay `docker-compose.vps.yml` подключает только `backend` к
постоянной внешней Docker-сети `rwms-logistics-private`. Один раз создайте
сеть с фиксированным gateway `172.21.0.1`, разверните
`deploy/nginx-rwms-private-bridge.conf` как конфигурацию Nginx и запускайте
Compose с обоими файлами. Nginx слушает только этот Docker gateway и проксирует
лишь `/oauth2/token` и `/api/internal/logistics/v1/planning/` к RWMS-сервисам,
привязанным к loopback.

Firewall хоста должен разрешать TCP только из `172.21.0.0/16` к этим двум
gateway-listener. Не привязывайте порты RWMS или этот мост к публичному адресу
VPS. `deploy/nginx.service.d/rwms-logistics-private-bridge.conf` запускает
Nginx после Docker, поэтому адрес постоянной сети существует и после reboot.

Полезные команды:

```bash
make up
make ps
make logs
make index-truck-restrictions
make down
```

`make reset-db` удаляет только Compose volume этого симулятора. Команда
намеренно явная, потому что удаляет все локальные данные стенда.
`make index-truck-restrictions` не меняет данные сценариев и пропускает уже
импортированную версию OSM.

## Тестирование

Полный контейнерный gate:

```bash
make test
```

Он запускает backend tests, Ruff и строгий mypy, затем frontend Vitest,
строгий TypeScript, ESLint и production build. Эквивалентные локальные
backend-проверки:

```bash
cd backend
python -m venv .venv
. .venv/bin/activate
pip install -e '.[dev]'
pytest
ruff check app tests
mypy app
```

Эквивалентные локальные frontend-проверки:

```bash
cd frontend
npm ci
npm run test:run
npm run typecheck
npm run lint
npm run build
```

При запущенном Compose выполните browser smoke flow:

```bash
cd frontend
npx playwright install chromium
npm run e2e
```

После изменения backend API пересоберите проверяемую транспортную границу:

```bash
make openapi
```

## Переменные окружения

| Переменная | По умолчанию | Значение |
| --- | --- | --- |
| `FRONTEND_PORT` | `5173` | Host-порт рабочего места |
| `BACKEND_PORT` | `8000` | Host-порт FastAPI и Swagger |
| `DATABASE_URL` | Compose PostGIS URL | Подключение SQLAlchemy к БД |
| `ROUTING_PROVIDER` | `valhalla` | Runtime adapter; `mock` только для тестов, `osrm` — явный legacy-вариант разработки |
| `VALHALLA_ENABLED` | `true` | Конфигурация завершается ошибкой, если выбранный Valhalla выключен |
| `VALHALLA_URL` | `http://valhalla:8002` | Приватный endpoint Valhalla, не публикуемый через Nginx |
| `VALHALLA_TIMEOUT_SECONDS` | `30` | Deadline одного truck-routing запроса |

## Синхронизация с RWMS

Интеграция с RWMS по умолчанию выключена. Для включения создайте выделенный
OAuth client `logistics-planner` в `auth-service`, задайте шесть переменных
`RWMS_*` выше и свяжите склад стенда через `external_warehouse_id` с UUID склада
RWMS. У водителей, которым можно применить маршрут, `external_worker_id` должен
содержать UUID соответствующего работника RWMS.

Оператор явно синхронизирует сценарий и диапазон дат через
`POST /api/scenarios/{scenario_id}/rwms/sync`. Стенд обновляет заказы по
стабильной идентичности `(scenario, RWMS, orderId)`, сохраняет версии заказов и
UUID бытовок из RWMS и классифицирует координаты по своим версионируемым зонам.
Если есть и адрес, и координаты, приоритет имеют координаты. Заказ только с
адресом возвращается как `COORDINATES_REQUIRED` и не импортируется: публичный
геокодер и выдуманный fallback координат не используются.

Ни одна транзакция БД стенда не остаётся открытой во время OAuth или RWMS HTTP
I/O. Sync закрывает read-транзакцию до получения feed; apply под коротким
локальным lock фиксирует команду точной версии плана, делает commit snapshot и
только затем выполняет идемпотентный удалённый вызов.

После проверки оператор применяет точную версию route plan через
`POST /api/plans/{plan_id}/rwms/apply`. Адаптер сопоставляет разбитые planning
parts с непересекающимися UUID бытовок и отправляет идемпотентную optimistic
команду назначения. Владельцем заказа и отгрузки остаётся RWMS, который
возвращает каждое успешное назначение и каждый отказ; устаревшая версия стенда
завершается конфликтом вместо перезаписи нового плана. Автоматическая граница
отклоняет назначения на сегодня и завтра: срочные изменения для этих дней
остаются явным ручным решением логиста в RWMS.

Нераспределённые доставки по умолчанию остаются видны только логисту. В окне
обмена с RWMS логист может явно отметить отдельные транспортные части и
опубликовать их как будущую общую работу `WAREHOUSE_DRIVERS`. Такое осознанное
действие разрешено на завтра, но не на текущий warehouse-local день, не создаёт
фиктивного водителя и повторно проверяется RWMS до preview и claim в DriverApp.
Публикация вывозов/возвратов этой границей пока не поддерживается.

В этом же окне `GET /api/plans/{plan_id}/rwms/status` читает состояние точной
версии плана. Для каждой будущей доставки видно, не опубликована ли она, доступна
ли всем водителям склада или уже взята конкретным водителем. Опубликованную или
взятую часть нельзя выбрать повторно; если авторитетный статус прочитать не
удалось, публикация в общий пул блокируется без догадок по локальному состоянию.
Перед read-only вызовом RWMS стенд освобождает свою транзакцию БД.

## Valhalla и грузовая маршрутизация OpenStreetMap

При `ROUTING_PROVIDER=valhalla` ограниченная Haversine-матрица служит только
предварительным фильтром комбинаций. Кандидат не считается допустимым, пока
каждый его участок отдельно не запрошен у приватного Valhalla с
`costing=truck` и собственным `EffectiveTruckProfile`. Точные distance/duration
Valhalla заново проверяют окна, конец смены и score. Сохранённые GeoJSON и
snapshot профиля используются карточками, линиями карты, диагностикой и
симуляцией.

Профиль содержит фактические высоту, ширину, полную длину автопоезда, полную
массу, число осей и настроенную максимальную реальную нагрузку на ось. Он
вычисляется из сохранённых машины, прицепа, платформы и размещения груза, а не
копируется из общего типа машины. Cache identity включает точки, профиль,
время отправления, версии provider и `OSM_DATA_VERSION`. Проверенная таблица
поддержки находится в
[`docs/osm-truck-restrictions.md`](docs/osm-truck-restrictions.md); неизвестные
conditional tags не выдаются в UI за безопасно учтённые.

В меню слоёв карты есть необязательный переключатель **Ограничения грузового
транспорта**. На масштабе 8 и крупнее он загружает ограниченную текущей областью
выборку PostGIS той же `OSM_DATA_VERSION`, показывает ограничения дорог
и точечные знаки с текстовыми маркерами, а по нажатию открывает теги и статус
поддержки. Частичные и неподдерживаемые теги явно помечены; слой не решает
допустимость маршрута и не заменяет truck costing Valhalla. OSM-отношения
ограничений поворота остаются логикой routing graph и не изображаются
выдуманными кликабельными линиями.

Граф не получает живой traffic feed: длительность определяется собранным OSM,
а не пробками Яндекса. Для смены региона обновите `OSRM_DATA_URL` и
`OSM_DATA_VERSION`, затем явно перестройте routing volumes; отдельный PostGIS
volume сценариев при этом не удаляется. Attribution OpenStreetMap остаётся в
MapLibre. Приватный router нельзя публиковать наружу.

Только для legacy-разработки можно выполнить
`docker compose --profile legacy-routing up osrm`; выбранный `osrm` не является
безопасной грузовой маршрутизацией и никогда не включается автоматически.

## MockRoutingProvider

Явный тестовый провайдер не использует сеть. Он вычисляет Haversine distance,
применяет road factor сценария, выбирает среднюю скорость города/области,
учитывает простой traffic multiplier по времени отправления и возвращает
distance, duration, данные участков и GeoJSON LineString. Одинаковые входы и
seed дают одинаковый результат. Ключ матричного кэша включает точки, routing
settings, временной bucket отправления и версию сценария.

## Настройка машины, прицепа и груза

Откройте **Машины**, создайте или измените машину и заполните раздел
**Грузовая маршрутизация**: собственную/максимальную массу, габариты, параметры
осей, геометрию платформы, ограничения груза и safety margins. В том же рабочем
месте создайте прицеп, выберите его как основной совместимый прицеп машины и
укажите либо точную длину автопоезда, либо длину сцепки для её расчёта. Затем
задайте измеренный `maxActualAxleLoadKg` для каждого используемого рабочего
состояния; приложение намеренно не делит общую массу на число осей.
Для автопоезда это максимальное измеренное значение среди всех осей машины и
прицепа, а не отдельный вектор по компонентам, поэтому пределы каждого
компонента всё равно требуют эксплуатационного замера. Поля машины и полный
набор осевых профилей сохраняются одной backend-
транзакцией, поэтому ошибка валидации не оставляет частично изменённую машину.

До сохранения форма показывает preview для одной и двух бытовок. Генератор
создаёт заявки с введёнными там габаритами груза; редактор ручной заявки
принимает такой же полный набор длины, ширины, высоты и массы. Текущий planning-
контракт RWMS эти физические поля не передаёт, поэтому новая импортированная
RWMS-заявка явно остаётся `ROUTING_PROFILE_INCOMPLETE`, пока оператор не введёт
измеренные значения; стенд их не угадывает. В готовом плане откройте
машину/цикл и разверните **Диагностику маршрута**, чтобы увидеть неизменяемый
профиль каждого участка. Старый сегмент без snapshot явно помечается
непроверенным и не может оставаться locked при повторной оптимизации Valhalla.

Интеграционный тест реального движка строит одноразовый OSM-граф с тегами и
доказывает: машина длиной 9 м выбирает короткую дорогу, а автопоезд длиной 18 м
обходит её ограничение `maxlength=12`. На том же графе проверяются высота,
ширина, полная масса, осевая нагрузка и `hgv=no`:

```bash
make test-valhalla-truck
```

## Эвристический планировщик

`HeuristicPlanner` намеренно моделирует рабочий шаблон
«доставки, затем вывозы», а не изображает универсальный VRP solver. Он:

1. проверяет смены/ресурсы на дату и разбивает готовые заявки;
2. строит детерминированную travel matrix;
3. сортирует доставки по hard/последней дате, ручному priority, дефициту дат и
   узкому окну, затем собирает равноприоритетные задания от ближних к дальним;
4. рассматривает ограниченное число пар доставок и оба порядка;
5. рассматривает не более `max_candidate_neighbors` групп вывозов с наименьшим
   крюком для каждой группы доставок, оставляет только группы внутри обоих
   лимитов;
6. сравнивает смешанный черновик с одним ограниченным контрольным планом только
   доставок и восстанавливает его, если упало покрытие обязательных, последних
   по дате или всех доставок, а затем добавляет вывоз только через полную
   валидную перепланировку остатка смены;
7. разрешает тому же водителю следующий загруженный на складе цикл и создаёт
   pickup-only циклы со штрафом, только когда допустимых доставок не осталось;
8. глобально назначает следующий лучший цикл свободному водителю;
9. сравнивает подключение ресурса с нагрузкой водителя с учётом перерыва;
10. выполняет ограниченные и полностью валидируемые локальные улучшения;
11. сохраняет метрики, объяснения, причины и ограниченный trace.

По достижении time/iteration limit движок предсказуемо возвращает лучший
найденный валидный план. Seed сохраняется в optimization run.

## Demo и воспроизводимость

При первом запуске создайте сценарий, откройте **Сценарий** в левой панели и
выберите **Demo scenario**. Также можно сбросить любой выбранный сценарий к
demo-состоянию после подтверждения замены данных только этого сценария. Выберите
demo planning date и нажмите **Построить маршруты**.
Demo можно безопасно изменять и создать заново. Его основной смешанный цикл —
`склад -> доставка -> доставка -> вывоз -> вывоз -> склад` с загрузкой
`2 -> 1 -> 0 -> 1 -> 2 -> 0`. Этот воспроизводимый стенд использует описанный
выше локальный для сценария лимит 60 минут/3,0. Mock routing повторяет эту
иллюстративную последовательность точно; Valhalla выбирает грузовой безопасный
эквивалент на своём OSM-графе.
В обоих случаях каждая машина сначала доставляет, затем забирает, соблюдает
загрузку `0..2` и возвращается на склад. Настройки по умолчанию у новых
сценариев не меняются.

Для экспериментов с датами и вместимостью используйте **Тест на 3 дня**. Он
никогда не сбрасывает открытый сейчас сценарий. Переключатель даты сверху,
chips в **Заявках** и карта показывают один и тот же набор заявок, доступных в
этот день. Нажмите маркер **Д** (доставка) или **В** (возврат), чтобы увидеть
его данные в popup над точкой и выставить на конкретную дату прямо на карте.
Для проверки зон выберите **Сделать вырез**, нажмите исходную зону и обведите
внутреннюю область. Заполните форму новой зоны: вырез исходной и создание
внутренней зоны сохраняются вместе. Оба действия — тестовая фиксация решения
логиста, а не подтверждение производственной отгрузки.

Для настраиваемой нагрузки выберите **Генератор заявок** в текущем сценарии.
Окно открывается в режиме одного дня без альтернативных дат. Задайте первую
дату, горизонт от одного до 31 дня, точное ежедневное количество от нуля до
десяти доставок и от нуля до десяти вывозов, от нуля до трёх дополнительных
допустимых дат для каждой заявки и seed. Дополнительные даты выбираются только
внутри горизонта. Начальные параметры груза — 6000×2400×2400 мм и 1200 кг;
перед генерацией их можно изменить. Каждый запуск сначала удаляет все
сохранённые планы, дата которых входит в выбранный горизонт, затем удаляет
заявки этого генератора с основной датой внутри горизонта и создаёт новый набор
в той же транзакции БД. Второй сгенерированный набор к той же дате не
добавляется. В ответе показывается количество удалённых планов и заменённых
заявок. Каждая созданная заявка сразу назначается на основную дату;
дополнительные допустимые даты остаются для последующего ручного решения
логиста, но автоматически не переносят работу на другой день. Ручные и
RWMS-заявки, сгенерированные заявки других дат и планы других дат не выбираются.
Если привязка к дороге или последующий этап генерации завершится ошибкой,
транзакция восстановит прежние планы и нагрузку. Действие **Удалить нагрузку**
удаляет и сгенерированную нагрузку, и все сохранённые планы даты, выбранной
сверху, не создавая замену. Каждая исходная координата находится внутри
текущего Polygon или MultiPolygon. При
Valhalla она привязывается к дороге через `/locate` и
принимается только тогда, когда дорожная точка всё ещё покрывается этой зоной;
если доступной дороги внутри зоны нет, вся атомарная генерация завершается с
`422 NO_ROUTABLE_POINT_IN_ZONE`. Mock-provider сохраняет детерминированную
исходную точку для offline-тестов. Затем обычная backend-классификация создаёт
заявку и её транспортные части. Одинаковые геометрия, routing graph, параметры
и seed воспроизводят одинаковые предметные значения.
Новые сгенерированные заявки также получают стабильные идентификаторы источника.
Пока датированная нагрузка не заменена, автопланирование назначает только
старейший логический источник среди старых повторов, а остальные показывает с
причиной `DUPLICATE_ASSIGNMENT_CONFLICT`. При замене такие строки генератора
удаляются вместе с планами затронутых дат. Новые строки используют стабильный
внешний ID; старые строки генератора без него сопоставляются по направлению,
точным координатам и основной логистической дате, а не по изменяемому номеру,
заметке или количеству. Поэтому переименование отображаемого `№3` в `№7` не
создаёт повторную поездку. Реальные ручные и RWMS-заявки
сохраняют свои авторитетные идентификаторы, даже если два клиента осознанно
указали один адрес. Клонирование сценария и JSON-экспорт/импорт сохраняют
систему-источник, внешний идентификатор, версию и source payload, поэтому
воспроизводимость не отключает защиту от повторов или lineage синхронизации с
RWMS.

Каждая зона также хранит две независимые неотрицательные тестовые цены в целых
рублях: за доставку и за вывоз. Применимый тариф виден в редакторе, списке зон и
popup заявки. Изменение тарифа не меняет версию геометрии или допустимость
маршрута и сохраняется при клонировании, JSON-экспорте и импорте.

В действиях сценария выберите **Экспорт JSON**. Один файл может включать
settings, географию, ресурсы, заявки/варианты дат, seed и выбранные сохранённые
планы вместе с source identity заявок. **Импорт JSON** проверяет весь документ
в одной транзакции; ошибка не
создаёт частичный сценарий. Экспорт нужен для bug report и воспроизведения
планировщика по seed и не должен содержать production-данные клиентов.

## Ограничения MVP

Это внутренний планировочный стенд, не production dispatch system. В нём
локальный audit actor `local-admin`, нет интерактивной production
identity/access model, реального трафика/GPS, встроенного приложения водителя,
push, клиентского checkout и платежей. Опциональный machine-to-machine доступ к
RWMS ограничен отдельным planning scope. Valhalla использует закреплённую
статическую выгрузку OSM и не знает живые пробки/перекрытия без отдельного
feed. Поддерживаемые и неподдерживаемые truck-теги документированы; система не
заявляет полную поддержку произвольных conditional numeric restrictions.
Геометрия mock-маршрута остаётся прямой GeoJSON polyline только для
детерминированных тестов.

Из P1 уже реализованы сохраняемые фазы/candidate events планировщика,
клонирование плана и симуляция недоступности водителя. За пределами текущего
MVP намеренно остаются:

- экран сравнения сохранённых планов;
- отдельный workflow рисования нового MultiPolygon несколькими контурами
  (импорт, хранение, отображение и редактирование существующих MultiPolygon
  поддерживаются);
- ручной split/merge циклов и полный remaining-day replan от
  интерполированной текущей позиции машины; текущая повторная оптимизация
  сохраняет locked-циклы и строит незаблокированную работу от склада;
- полный набор межцикловых операторов локального поиска (автоматический
  перенос/обмен циклов, замена вывоза и split/merge). Ограниченный пост-проход
  сейчас проверяет оба порядка доставок и вывозов; перенос и перестановка задач
  между циклами доступны через валидируемый backend ручной редактор;
- линии кандидатов с координатами в каждом trace event; реальные фазы и решения
  по кандидатам сохраняются, но UI рисует линию только при наличии координат в
  событии;
- внешний optimization worker с прерываемой live-отменой. Текущая ограниченная
  эвристика выполняется внутри API-процесса и возвращает terminal run, поэтому
  сохраняемый cancel flag является интеграционной границей, но не надёжно
  прерывает уже выполняющийся запрос;
- адаптер Yandex/другого traffic-aware routing, OR-Tools/CP-SAT engine,
  production-auth, сертификация high-volume benchmark и дополнительные типы
  инцидентов.

Production frontend сейчас выдаёт предупреждение Vite о крупном chunk (около
1,70 MB до gzip); route-level code splitting остаётся оптимизацией и не мешает
запуску приложения.

## Подключение другого реального routing provider

Реализуйте `RoutingProvider.get_matrix()` и `get_route()` в
`backend/app/routing`, верните существующий typed-контракт
distance/duration/legs/geometry, добавьте provider-specific config и выберите
адаптер через `ROUTING_PROVIDER`. Credentials должны оставаться на сервере;
нужны timeout/rate-limit/cache и общие provider contract tests. Будущий Yandex
adapter не должен требоваться для mock-запуска и не может заменять финальную
доменную валидацию.

## Подключение OR-Tools или CP-SAT

Реализуйте протокол `PlannerEngine.generate_plan()` в `backend/app/planner`,
преобразуйте тот же immutable planning input/settings и верните тот же
валидированный контракт cycles, explanations, metrics, reasons и progress
events. Включайте движок явной конфигурацией и сохраняйте эвристику как
детерминированный вариант без дополнительной зависимости. Результат solver не
может обходить общий валидатор hard-инвариантов.
