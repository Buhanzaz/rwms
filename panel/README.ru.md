# Панель RWMS

`panel/` — React/TypeScript веб-панель для операционных пользователей RWMS.
Это браузерный клиент, а не фасад доменных сервисов: бизнес-команды,
авторизация, переходы состояния и хранение остаются у владеющих backend-сервисов.

English version: [README.md](README.md).

## Публичная граница и аутентификация

- Браузер обращается только к публичному API gateway на собственном origin:
  `/auth/**` для OAuth/OIDC и `/api/**` для публичных API. В конфигурации не
  должно быть внутренних адресов сервисов, service-port на `localhost` или
  маршрутов `/api/internal/**`.
- Интерактивный вход использует OIDC-flow gateway. Панель принимает человека с
  principal `USER`; gateway и владеющий сервис всё равно проверяют каждую роль
  и доступ к складу. Скрытие UI-контрола не является авторизацией.
- Vite proxy — только удобство локальной разработки. В production запросы
  браузера остаются same-origin и должны обслуживаться публичным gateway.

## Продуктовая поверхность и владение состоянием

Роутер открывает операционную панель склада/оборудования, аренды и заказов,
инвентаризации, обслуживания/приёмки, логистики, доски задач, ассистента,
списаний и настроек. Текущий профиль пользователя определяет доступные
контексты складов и экраны.

- TanStack Query хранит серверные чтения; query keys включают нужные склад,
  сущность и параметры фильтра. Авторитетным остаётся сервер.
- Выбранный склад — неавторитетное локальное UI-предпочтение. После входа он
  перепроверяется по профилю.
- Настройки бригад доски задач одной командой группы отправляют выбранный состав
  и version-fenced изменения текущей бригады работников. Второго действия
  назначения в таблице работников нет: task-board атомарно применяет либо
  отклоняет всё изменение.
- Проверенный аутентифицированный subject и его bearer grant revision владеют
  отдельным вложенным TanStack Query client. Logout, смена subject или grant
  перемонтируют защищённый subtree и тем самым останавливают effect-owned
  realtime streams, отменяют и удаляют защищённые query и mutation state и
  очищают media blob URL до монтирования следующего защищённого subtree.
  Корневой client сохраняет public offer и bootstrap state.
- SSE потоков assets и media — это invalidation-сигналы, а не вторая доменная
  проекция. Их обработчики обновляют или patch-ят только затронутые query и
  удаляют media blob с изменённой ревизией; глобальной очистки cache нет.
- Досье бытовки принимает полный канонический словарь activity. Подготовка и
  завершение передачи ремонта отображаются в истории ремонта с immutable
  snapshot склада, возвращённым `dossier-service`. Факт титульного фото
  завершённого задания становится activity истории с opaque media ID,
  generation и ID задания, но никогда не с object-storage URL; точную границу задают
  [OpenAPI dossier](../contracts/openapi/dossier-service.yaml) и строгая
  [модель activity панели](src/features/rental-items/dossier/model/dossier-service.ts).
- Вкладка бытовки «История» показывает эти канонические activity как компактный
  хронологический раскрываемый таймлайн. Связанные факты сметы, ремонта,
  инвентаризации и media группируются только по их каноническим source ID или
  folder ID; прошлые операции отмечены зелёным, а последняя загруженная — синим.
  При раскрытии видны точные данные сервера о времени, исполнителе, состояниях
  media, составе событий и доступном переходе в принадлежащий домену процесс без
  домысливания отсутствующих доменных данных; защищённый технический режим
  сохраняет исходные метаданные источника. «Открыть фото задания» разрешает
  только эту opaque reference через публичный `TASK_BOARD_ENTRY` media owner
  proof и bearer-сессию caller-а. См. [регистр activity](src/features/rental-items/dossier/dossier-activity-register.tsx).
- Если постановка ремонта в очередь возвращает точный код Problem Details
  `BOOKED_UNIT_REPLACEMENT_REQUIRED`, редактор ремонта сохраняет ID и версию
  записанного черновика задания, закрывает диалог завершения и показывает
  «Бытовка забронирована» с действием «К заказам» в существующий маршрут
  `/orders`. Обычные ошибки очереди сохраняют стандартное сообщение без этой
  подсказки о замене. См. [редактор ремонтного задания](src/features/repair-tasks/repair-task-editor-workspace.tsx).
- Редакторы осмотра/финального плана инвентаризации, сметы и первичного ремонта
  передают явный выбор `forceCapitalRepair` через канонические команды и
  показывают серверное значение только для чтения, когда соответствующий план
  уже нельзя менять. В плане инвентаризации этот control расположен сразу после
  выбора перемещения на ремонт, а два направления взаимоисключающие. Для
  произвольной работы или материала выбирается явная очередь доски ремонта/
  ожидания; snapshot routing замороженных строк затем восстанавливает каждую
  строку ровно в одном этапе, в том числе при повторяющихся ID работ каталога.
  Новая переделка наследует выбор капремонта, поскольку её create-контракт не
  разрешает его заменять. Рассчитанные CAPITAL-ремонты продолжают использовать
  существующие отдельные поверхности капремонта и приёмки, а не таблицу обычных
  ремонтов. Их карточки на доске водителя загружают авторитетный план ремонта
  только при раскрытии и показывают упорядоченные очереди в отдельных колонках
  работ и материалов с точным количеством и единицами.
- Общие owner-media поверхности сначала показывают READY-изображения, затем
  READY-видео через сжатый MP4-вариант `PLAYBACK` с нативными controls. Можно
  добавлять JPEG, PNG, WebP, MP4 и WebM. Выбранный локальный оригинал появляется
  сразу, пока его same-origin upload продолжается в фоне; byte progress
  расположен непосредственно под preview, а действия обложки/удаления
  появляются только после готовности серверной записи. Обложкой назначается
  только изображение, а защищённые blob URL освобождаются при смене generation
  или owner scope. Карусель в карточке бытовки читает только проекцию текущей
  папки media-service, а фотоархив продолжает показывать все исторические
  папки. Если эта вспомогательная проекция обложки недоступна, но owner-media
  успешно загружены, карточка показывает полученные фото и не объявляет весь
  фотосервис недоступным. Складские карточки, карточки подбора, карусель паспорта
  и активная папка архива ставят явную обложку первой, сохраняя стабильный
  association order остальных фотографий; клиент применяет тот же порядок к
  ответу старой версии media-service, где обложка пришла позже. Вкладка «Фото»
  паспорта сначала показывает сохранённые media-owned папки, а на каждой папке —
  источник, время события, автора и количество фотографий. Она читает все
  страницы досье `INVENTORY`/`MEDIA` независимо от фильтров вкладки «История»;
  недоступный источник остаётся явно неизвестным, а не угадывается. Фотоархив
  также проходит все media cursor, а не останавливается после первых 100
  associations.
  Детали ремонтного задания держат общие media задания, source media каждой
  строки работы и итоговые evidence task-board в отдельных галереях по точным
  references. Общие галереи и evidence результата сохраняют стандартное общее
  представление, а галерея каждой строки работы использует компактную карусель
  со счётчиком на изображении и всегда видимыми кнопками назад/вперёд. Общие и
  построчные references используют исходный owner proof
  инвентаризации, сметы или ремонта; авторитетный источник инвентаризации имеет
  приоритет над устаревшими origin ремонта и ссылкой на смету. Только evidence
  результата исполнителя использует proof записи task-board. Галерея бытовки
  вместо них не подставляется. Для папок инвентаризации источник, время события и автор
  берутся из activity инвентаризации в досье. См. [hook фотографий
  бытовки](src/features/rental-items/use-rental-item-media.ts), [parser
  обложек](src/features/media/api/http-media-client.ts) и [media
  feature](src/features/media/).
- Панель может объединять независимые публичные чтения для экрана, но не должна
  оркестрировать межсервисные бизнес-процессы в браузере.

## Ассистент аренды, клиенты и заказы

- Уточнения ассистента образуют одну долговечную последовательность в порядке
  сервера. Панель показывает только вопрос `PENDING` с наименьшим номером и его
  точные серверные варианты, скрывает очередь и историю и отключает свободный
  ввод до успешного ответа. Устаревший или нарушающий порядок ответ с `409`
  перечитывает авторитетный вопрос. Независимых активных веток и нижней панели
  «Продолжить точный поиск» больше нет; обычные сообщения, результаты бытовок
  и действия клиентского представления остаются в диалоге. Карточки результата
  требуют одновременно тип бытовки и отделку, а активная логическая группа
  сохраняется при обновлениях выбора и потока. См.
  [OpenAPI ассистента](../contracts/openapi/assistant-service.yaml), строгий
  [адаптер ассистента](src/features/assistant/api/assistant-api.ts) и
  [страницу диалога](src/features/assistant/pages/assistant-page.tsx).
- Выборкой ассистента и сроком её блокировки владеет логистика. Снятие checkbox
  отправляет полный оставшийся набор ID с idempotency key; пустой набор
  освобождает hold, а частичное удаление применяет новый авторитетный срок.
  Потоковое удаление по команде LLM согласуется сразу, после чего terminal
  refetch перечитывает диалог. Браузер никогда не считает локальный набор
  checkbox авторитетным состоянием.
- Маршрут ассистента из заказа проверяет точные `clientId` и `orderId`, читает
  или создаёт диалог по контрактному `rentalOrderId` и передаёт уже известных
  клиента и заказ без второго выбора клиента. Склад заказа фиксирует логистика;
  браузер не выбирает другой склад и не выполняет saga автоматического
  архивирования и пересоздания диалогов.
- Навигация аренды открывает серверный постраничный grid клиентов `/clients` и
  карточку клиента `/clients/:clientId`. Заметное действие «Создать клиента»
  сверху справа открывает существующую форму клиента в модальном окне, создаёт
  через API логистики и поддерживает ноль или больше именованных дополнительных
  контактов без отдельной страницы. Основной и дополнительные контакты клиента
  остаются раздельными и показываются по имени и телефону в списке и карточке;
  собственные контакты заказа хранятся и отображаются отдельно. Карточка
  клиента читает его заказы и ведёт в чат, подбор по складу или ручное создание
  заказа, передавая для prefill только `clientId`. Исторический клиент с
  правдивым `null` вместо телефона показывается как «не указан» и никогда не
  дополняется вымышленным значением в браузере. См.
  [OpenAPI логистики](../contracts/openapi/logistics-service.yaml) и
  [feature клиентов](src/features/clients/).
- Бронирование запрашивает по 50 бытовок на серверную страницу и откладывает
  текст до настоящего запроса. Оно не опрашивает весь каталог по таймеру,
  компактный grid получает высоту по фактическому содержимому, а карточка
  сначала загружает одно превью; окончательная доступность и эффект hold
  остаются авторитетными на сервере. Истечение hold планирует одно обновление
  по сроку вместо перерисовки всего экрана каждую секунду. См. [каталог
  бронирования](src/features/booking/booking-catalog-page.tsx) и [hook
  истечения](src/features/booking/use-booking-hold-expiry.ts).
- Обычное бронирование поддерживается только как
  `/booking?clientId&orderId`. Оно проверяет точные заказ и клиента, фиксирует
  склад заказа (либо склад первой выбранной бытовки, пока у черновика его нет) и
  читает или создаёт прямой запрос логистики с `conversationId: null`. Скрытый
  диалог ассистента не создаётся, а активный AI-связанный запрос не
  переиспользуется. Маршрут без заказа показывает явное неподдерживаемое
  состояние.
- В каждой публичной карточке NORMAL используется подписанный чекбокс «Выбрать
  бытовку …». У выбранной бытовки доступно «Добавить наполнение»: оно открывает
  компактный прокручиваемый диалог вместо встроенного/полноэкранного редактора.
  Селектор типа показывает `Название: доступно — число`; клиент добавляет каждый
  тип один раз и меняет количество ограниченными кнопками `−`/`+`. Наполнение
  набирается независимо для каждой выбранной бытовки. Доступная ёмкость
  учитывает обновляемый общий остаток, собственный черновик этой бытовки и
  физическое содержимое выбранных удерживаемых бытовок без двойного учёта, затем
  применяет nullable `maximumPerCabin`. Представление опрашивает сервер и
  перечитывается при focus/reconnect; уменьшившийся остаток сохраняет понятный
  черновик, помечает его невалидным и отключает подтверждение, а атомарная
  серверная команда остаётся авторитетной. Публичное представление собирает от
  одной до пяти независимых date-only желаемых дат клиента; менеджерская деталь
  заказа показывает возвращённые значения только для чтения и не перезаписывает их.
- Представление REPLACEMENT требует точное серверное количество и сохраняет
  порядок кликов клиента. Редактора мебели в нём нет: желаемые количества
  остаются забронированными и переходят на соответствующую замену в текущем
  заказе. Если после выполненного перемещения мебель уже физически находится в
  старой бытовке, сервер создаёт её физическое перемещение в бытовку-замену.
  Постоянный отказ публичного бронирования завершает эту ревизию и просит у
  клиента обновлённую ссылку вместо локальной повторной попытки.
- Экран создания и редактирования заказа сохраняет только выбранного клиента,
  изменяемый контактный телефон заказа и комментарий. На втором шаге публичного
  представления клиент указывает адрес доставки, необязательную пару координат,
  ноль или больше собственных дополнительных контактов заказа, от одной до пяти
  независимо выбранных желаемых дат и первоначальный срок аренды. Возвращённые
  `desiredDeliveryWindows` в детали заказа показываются только для чтения как
  «Выбрано клиентом в представлении» и остаются отделены от назначенной
  логистикой даты. Деталь черновика
  требует непустого контактного телефона, выбранного склада и хотя бы одной бытовки;
  менеджер не получает команды для первоначального срока по отдельной бытовке.
  После фактической отгрузки/аренды карточка бытовки
  показывает длительность, дату отгрузки и расчётную дату возврата. Диалог
  «Продлить аренду» выбирает одну или несколько таких бытовок, показывает
  желаемую и фактическую мебель только как информацию и отправляет общий срок
  через существующую версионированную идемпотентную команду
  `POST /orders/{id}/rental-terms/extend`. Диалог контактных данных сохраняет
  выбранного клиента. Сохранение переводит заказ в сохранённое состояние для
  обработки в «Заданиях», но не создаёт отгрузку или рейс.
- Если сервер разрешает редактирование заказа, действие «Добавить бытовки»
  доступно и в DRAFT, и в SAVED, в том числе после добавления первой бытовки.
  Диалог предлагает ровно два связанных пути: AI-чат и обычное бронирование;
  оба получают текущие `clientId` и `orderId`; ни один путь не блокируется
  введёнными менеджером желаемыми датами, потому что дату и срок аренды
  клиент выбирает в представлении. Устаревшего встроенного расклада бытовок
  больше нет. Серверные проекции показывают
  состояние резерва каждой бытовки и каждой строки желаемой мебели. Редактор
  мебели ограничивает строку одновременно общим доступным количеством и
  `maximumPerCabin`, не урезая молча уже сохранённое количество этого заказа;
  при конкурентном конфликте перечитываются авторитетные заказ и каталог.
  Деталь заказа также показывает
  принадлежащие логистике плановые/фактические отвозы и возвраты, затем
  независимо читает публичное досье выбранных бытовок. Отсутствие сметы или
  ремонта считается доказанным только после полного чтения всех страниц
  проекции досье; partial, ошибочное или ещё не завершённое постраничное чтение
  явно остаётся неопределённым. См. [адаптер заказов](src/features/orders/api/orders-api.ts),
  [деталь черновика](src/features/orders/pages/order-detail-page.tsx), [диалог
  доставки](src/features/orders/components/order-delivery-dialog.tsx) и
  [доказательства досье](src/features/orders/components/order-unit-dossier-evidence.tsx).
- Независимая серверная проекция `permissions.canReplaceUnits` показывает
  действие «Заменить бытовки», даже когда обычное редактирование заказа уже
  закрыто. Менеджер сначала выбирает существующие бытовки заказа, затем
  использует ровно один из двух режимов: существующий маршрут бронирования
  получает упорядоченные повторные параметры `replacementUnitId` для выбора
  клиентом, а самостоятельная замена принимает ровно одну старую бытовку,
  обязательную причину и свободного кандидата того же склада из границы заказа.
  Ответ версионированной идемпотентной команды обновляет текущий заказ с
  проекцией перенесённой мебели; конфликт перечитывает заказ и кандидатов, не
  очищая черновик замены. См. [диалог
  замены](src/features/orders/components/order-unit-replacement-dialog.tsx) и
  [адаптер заказа](src/features/orders/api/orders-api.ts).

## Логистическая доска водителей

- Формы отгрузки и возврата выбирают активного водителя по opaque worker ID.
  У складского перемещения нет ответственного водителя, потому что оно создаёт
  общую складскую работу.
- Раскрытые строки `/logistics/order-tasks`, `/logistics/shipments` и
  `/logistics/returns` перед списком бытовок показывают связанный заказ и сводку
  по клиенту: адрес, именные контакты, телефоны, координаты, срок аренды и
  водителей отвоза/возврата, когда доступны их авторитетные чтения. Для каждой
  бытовки желаемая мебель заказа сравнивается с её текущим наполнением из
  asset-service и показывается текстовый статус: требуется наполнение,
  требуются действия, загружено, наполнения нет или данные недоступны. Диалоги
  планирования повторяют сводку наполнения ровно для бытовок будущей команды.
- Адаптер складских перемещений проверяет полную актуальную форму документа
  логистики. Ответ перемещения требует пустые поля водителя и связанной
  арендной отгрузки и явно отклоняется, если обязательных полей нет или в них
  пришли данные отгрузки; панель не имитирует успешное перемещение.
- `/logistics/board` показывает только карточки отгрузки и возврата в
  горизонтальных колонках календарных дат. Внутри каждой даты находятся
  независимо сворачиваемые очереди активных водителей и очередь «Не назначено»
  только при наличии таких карточек. Текущая и плановая очереди остаются
  раздельными внутри одной секции водителя; карточки также сворачиваются.
- Датированная доска выводит только сгруппированные проекции отгрузки/возврата:
  legacy-карточки без проекции ходки и transfer скрыты. Заголовок карточки —
  «Отгрузить бытовку» или «Вернуть бытовку», без номера задания/ходки и raw
  legacy-текста. Показывается «Дата выполнения задания», но не пожелание
  клиента. У каждой бытовки фактическое наполнение имеет вид `Название: Nшт` и
  ровно один итоговый статус: серый «Нет наполнения», оранжевый «Ожидает
  наполнения», жёлтый «Ожидает выноса наполнения» или зелёный «Наполнение
  готово».
- Логистическую карточку можно переставить только внутри её текущей даты, lane и
  очереди водителя. Клиент отправляет версии task/entry и новую позицию, но не
  меняет аудиторию водителя через drag and drop.
- `/logistics/tasks` является отдельной общей доской складских перемещений. Она
  сохраняет transfer, свободные перемещения, ремонтные места и капитальные
  ремонты без секций водителей и водительской identity в интерфейсе.
- Optimistic movement является только состоянием представления. При отказе
  восстанавливается прежняя доска и перечитывается авторитетная projection;
  ошибка справочника водителей не блокирует известные задачи и команды доски.

См. [канонический контракт логистики](../contracts/openapi/logistics-service.yaml),
[модель доски](src/features/logistics/driver-board/driver-board-model.ts) и
[логистическую доску](src/features/logistics/driver-board/logistics-board-page.tsx),
[доску перемещений](src/features/logistics/driver-board/driver-board-page.tsx) и
[адаптер складских перемещений](src/features/logistics/warehouse-transfers/adapters/http-warehouse-transfer-client.ts).

## Ошибки, конкурентность и команды

Общий bearer-клиент преобразует gateway Problem Details в `ApiError` с HTTP
статусом и машиночитаемым кодом. Отсутствующая сессия, недоступный gateway или
неподдерживаемая публичная операция показываются как явная ошибка; mock-success
fallback отсутствует.

Обычные HTTP-запросы ассистента и stream turn ассистента используют одно
безопасное преобразование Problem Details. `401` остаётся сигналом
обновления аутентификации/повторного входа, `403` требует обновлённых grants
или действия пользователя, а `409` требует авторитетного пути
refetch/conflict. Некорректное тело Problem Details всё равно возвращает
`ApiError` со статусом и безопасным fallback-сообщением.

Добавление media использует ограниченную очередь из четырёх upload worker со
стабильными idempotency key и упорядоченным результатом. Первая ошибка не даёт
запускать новые jobs, дожидается уже начатых transfer и возвращает именно эту
первую ошибку, не имитируя частичный успех. Browser byte progress использует тот
же аутентифицированный same-origin content route, не изменяет media contract и
не делает локальный preview авторитетным.

Для изменяющих операций используйте fencing, заданный канонической OpenAPI
операцией (`expectedVersion`, ETag или эквивалент), и единый путь
refresh/retry для `409 Conflict`. Повторяемые create/effect требуют
idempotency key контракта или стабильный внешний идентификатор. Не делайте вывод
об успехе команды только по обновлению cache или SSE-уведомлению.

При сохранении осмотра инвентаризации панель перечитывает текущую сессию и
использует её общий session revision, но сохраняет finding revision, с которым
был открыт редактор. Поэтому изменение другой бытовки не блокирует дополнение,
а конкурентная правка этой же бытовки по-прежнему завершается безопасным `409`.

На MANAGE-экране завершения инвентаризации в проверке бытовок и мебели доступна кнопка
**«Пересчитать изменения сессии»**. Она недоступна, пока есть несохранённый черновик сверки/плана
или выполняется конкурирующая команда завершения. Команда обновляет авторитетный состав на сервере;
после успеха панель сохраняет записанные осмотры бытовок, заменяет detail сессии и удаляет только
производные кэши реестра, мебели, статистики, итогового плана и preview завершения, чтобы сверку
можно было построить заново по текущим данным.

В истории завершённой инвентаризации доступно отдельное MANAGE-действие
**«Пересчитать и применить итоги»**. Оно отправляет точную ревизию завершённой
сессии и версию/hash итогового плана с idempotency key в публичную границу
inventory. Обязательное подтверждение объясняет, что инвентаризация становится
текущей истиной: бытовки без работ получают `FREE`, с обычными работами —
`REPAIR`, с принудительным капремонтом — `CAPITAL_REPAIR`, а активные привязки
аренды, резерва, внутреннего перемещения или прежнего ремонта могут быть
замещены. Обычная работа без входящего перемещения направляется на task-board,
перемещение ждёт логистической доставки, а капремонт остаётся в активном
capital-route. Само применение итогов никогда не открывает приёмку или
доработку. Фотографии, доказательства и история сохраняются. Действие недоступно
без идентичности завершённого итогового плана или во время конкурирующей команды
истории. Принятый ответ обновляет кэш публикаций и перечитывает только затронутые
запросы detail сессии, итогового плана, статистики и истории склада. Ответ может
содержать строго следующую исправленную version/hash итогового плана, если сервер
восстановил исключённое явное наблюдение. Панель принимает этого авторитетного
преемника и перечитывает его head; меньшая версия или другой hash в той же версии
остаются конфликтом. В завершённой истории колонка статуса по итогу показывает
обязательный `desiredAssetStatus` (`FREE`, `REPAIR` или `CAPITAL_REPAIR`) текущей
операции публикации только после её успеха и добавляет отметку перемещения при
`movementToRepair`. Текущая ожидающая или неуспешная операция показана как
неприменённая; панель никогда не выдаёт за финальный статус зафиксированный снимок
осмотра. Активные сессии, отменённая история и строки без операции итогов продолжают
показывать записанный снимок как доказательство осмотра. Авторитетный
контракт — [OpenAPI inventory](../contracts/openapi/inventory-service.yaml).

## Локальная разработка и проверки

Из этого каталога с актуальной Node.js LTS:

```bash
npm ci
npm run dev
npm run typecheck
npm test
npm run lint
npm run build
```

`npm run dev` слушает `localhost:8080`; его proxy target предназначен только
для локальной разработки. До заявления об интеграции или релизе настройте и
проверьте настоящий публичный gateway origin.

## Правила релиза

Собирайте только из целевого reviewed source scope. Release bundle нужно
проверить через same-origin `/auth/**` и `/api/**`: первый вход,
чтение профиля/workspace, разрешённую команду, путь `409` где он применим и
обновление по invalidation. Нельзя публиковать артефакт, собранный из другого
checkout или смешанного непроверенного worktree.

## Текущие ограничения

- Защищённые серверные данные и media blob должны оставаться внутри client
  boundary ревизии. Не добавляйте browser store, unscoped object-URL cache или
  прямую запись защищённого state в root client: они обходят fence subject и
  grant.
- Streaming path ассистента разделяет преобразование Problem Details обычного
  bearer-клиента; не добавляйте вторую политику статусов или тела ошибки.

## Источник истины

Семантика публичных операций находится в `contracts/openapi/`, семантика
событий — в `contracts/events/`. Gateway владеет маршрутизацией и проверкой
токена, но не бизнес-агрегацией. UI-изменения проверяйте одновременно с
владеющим сервисом и каноническим контрактом.

Общая граница failures реализована в
[`src/lib/api-client.ts`](src/lib/api-client.ts), а stream ассистента использует
её из [`src/features/assistant/api/assistant-api.ts`](src/features/assistant/api/assistant-api.ts).
