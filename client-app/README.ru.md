# RWMS CustomerApp

CustomerApp — нативное Android-приложение клиента для бронирования бытовок.
Application ID — `dev.buhanzaz.rwms.client`, минимальная ОС — Android 11
(API 30), compile/target SDK — 36. Приложение независимо от ManagerApp и
WorkerApp.

English version: [README.md](README.md).

## Владение и границы

Приложение обращается только к публичному gateway из
`RWMS_PUBLIC_BASE_URL`. Для аутентификации используются `/auth/**`, для аренды
клиента — `/api/logistics/customer/v1/**`, а доказательства проблем и аватары профиля используют
same-origin поток `/api/media/v1/**` upload-session/content/finalize. Серверные данные остаются
авторитетными: приложение локально не создаёт доступность бытовок, остатки
мебели, слоты доставки или успешное бронирование.

## Аутентификация

Вход выполняет OAuth 2.0 Authorization Code с S256 PKCE для клиента
`rwms-customer-android`. Логин/пароль и cookies Spring-сессии существуют только
во время одного native-обмена и никогда не сохраняются. Callback
`https://localhost/auth/customer/callback` разбирается и проверяется внутри
процесса, а не открывается. Регистрация сначала получает CSRF metadata,
отправляет подтверждённый пароль, затем запускает тот же PKCE-вход.

Каждый запуск процесса сначала ровно три секунды показывает точный импортированный
векторный логотип BLOCK BOX. Стартовые кнопки въезжают с противоположных краёв экрана
без родительского alpha-слоя, обрезающего движение. Логотип занимает ширину кнопок и
перемещается над формой; клавиатура сворачивает отведённое ему место, а вся форма
остаётся прокручиваемой. Вход, регистрация и восстановление используют короткие
переходы между состояниями одного signed-out экрана. У входа есть заголовок `Вход`
и кнопка `Войти`; возврат назад использует тот же переход.
Регистрация собирает логин, email, подтверждённый пароль и телефон; auth boundary
по-прежнему получает только поля своего контракта, а email и телефон подставляются
в обязательный профиль физлица после входа. `Продолжить без аккаунта` остаётся
видимым, но недоступным: публичного контракта гостевого каталога нет. Восстановление
возвращает честную заглушку, а не имитирует успех.

Один беззвучный Media3 player показывает точный импортированный
`background_caustic.webm` под всеми маршрутами CustomerApp. Видео заполняет экран
через crop/zoom, бесконечно повторяется, приостанавливает декодирование вне активного
lifecycle и освобождается вместе с корневой composition, не создаваясь заново между
экранами. Поля auth/профиля и действия приложения переиспользуют полупрозрачные поля
и градиентные кнопки с радиусом 12 dp и сдержанной анимацией нажатия. Заголовки Manrope
и основной текст Golos Text поддерживают кириллицу; шрифты поставляются вместе с
SIL Open Font License в `app/src/main/assets/licenses/`. Рабочие экраны используют
более читаемые полупрозрачные поверхности, отдельный контурный стиль второстепенных
действий и области нажатия от 48 dp. Тени кнопок рисует кешируемый Compose `dropShadow` по форме
компонента независимо от прозрачной заливки; у полей светлый контур без elevation-слоя. Выбор даты и времени показывает
адрес, серверные предложения и цену без внутренних счётчиков вместимости и габаритов
профиля машины; подтверждённое условие проезда остаётся на экране оформления. Motion foreground — в
[`CustomerStoreWelcomeScreen.kt`](app/src/main/java/dev/buhanzaz/rwms/client/ui/CustomerStoreWelcomeScreen.kt),
общий visual/player слой — в
[`CustomerStoreDesign.kt`](app/src/main/java/dev/buhanzaz/rwms/client/ui/CustomerStoreDesign.kt),
conditional-привязка — в
[`CustomerApp.kt`](app/src/main/java/dev/buhanzaz/rwms/client/ui/CustomerApp.kt).

При включённом `Запомнить` access/refresh tokens хранятся в DataStore как AES-GCM ciphertext;
без него рабочая сессия остаётся только в памяти процесса. Ключ —
неэкспортируемый материал Android Keystore. Отклонённый access token
обновляется один раз; повторный 401 завершает сессию, а при 409 приложение
перечитывает авторитетную корзину и инвалидирует устаревшие данные слота
доставки. Отдельный неавторитетный указатель DataStore хранит только ID
выбранного склада, явное предпочтение «запомнить склад», ID inquiry и стабильный idempotency key
создания inquiry. Он очищается при выходе и после пересоздания процесса перечитывает inquiry только
при включённом предпочтении; иначе клиент возвращается на отдельный шаг выбора склада.
Повтор в том же процессе после неопределённого ответа создания использует этот
незавершённый ключ, а не открывает другую inquiry.
Отдельный ограниченный неавторитетный реестр DataStore хранит только стабильные UUID незавершённых
request fingerprint приёмки бытовки и сообщения о проблеме. Он переживает пересоздание процесса,
никогда не вытесняет незавершённый ключ и удаляет ключ только после ответа сервера либо сверки
авторитетного результата по списку заказов; payload команд и серверные результаты в нём не хранятся.
Если восстановленная серверная session имеет состояние `BOOKED` или `CANCELLED` либо cart-scoped
чтение возвращает стабильный problem code `INQUIRY_ARCHIVED`, CustomerApp сохраняет
завершённый заказ и выбранный склад, но атомарно заменяет указатель новым durable
create key до открытия следующей корзины. Заказ прежней inquiry не блокирует
изменения в новой корзине.

## Клиентский поток

После оформления «Мои заказы» показывают неизменяемый серверный счёт как фирменный нефискальный
чек с суммами справа и выделенным точным итогом: аренду бытовок, мебель по формуле количество × цена единицы за месяц × срок
этой бытовки, согласованную доставку один раз и точный итог в целых рублях. Не включённая в счёт
доставка явно не рассчитана, а не бесплатна. Суммы не используют floating point или int64 для
накопления итога. Пятиминутный отсчёт опирается на серверное и монотонное время; статус оплаты
меняет только ответ сервера. Тестовая оплата требует явного нажатия и не списывает реальные деньги.
Потеря ответа сохраняет durable-ключ бронирования/версии; сверка проверяет точный заказ и тот же
неизменяемый счёт. Старые бронирования без выставленного счёта не показываются оплаченными.
Для сохранённого заказа без серверного окна оплаты чек объясняет, что срок оплаты и автоматическая
отмена по таймеру не назначены. Отменённый заказ показывает отменённую доставку и не предлагает
приёмку по устаревшим данным о прибытии.

При активном lifecycle приложение обновляет заказы, ожидающую оплату и серверные непрочитанные
уведомления. Только кнопка «Прочитано» подтверждает чтение на сервере. Системное уведомление
открывает приложение через immutable explicit intent без данных заказа и credentials; ограниченный
локальный список ID доставки предотвращает повторные сигналы, но не хранит состояние домена.
WorkManager проверяет сервер при наличии сети после срока оплаты и периодически раз в 15 минут,
не более восьми попыток на выполнение. Android может отложить фоновую работу; сервер снимает
резерв независимо от устройства. Нужны разрешение ОС и, после завершения процесса, зашифрованная
сессия с выбранным «Запомнить». Выход отменяет работу, убирает уведомления и отсекает поздние ответы.

Jetpack Compose Material 3 и Navigation 3 дают взаимоисключающие signed-out и
signed-in графы. Каждый новый клиент завершает регистрацию как физлицо. Тип уже
существующего профиля физлица/юрлица остаётся неизменяемым; в drawer есть намеренная
заглушка `Доступ для юрлиц` для будущего отдельного доступа. Затем клиент выбирает город с необязательным
checkbox «Запомнить выбранный город», после чего загружаются возвращённые сервером свободные бытовки.
Меню и профиль доступны уже при выборе города. Название берётся из поля `city` warehouse-service;
склады одного города сохраняют отдельные ID и различаются адресом/именем. Стеклянная шапка с отступами
центрирует город между меню и профилем. Нажатие раскрывает альтернативы под фиксированной строкой,
затем создаёт либо возобновляет inquiry выбранного склада. Кнопка фильтров без подложки раскрывает
под шапкой сетку из двух равных колонок: тип, отделка, размер, категория,
линолеум и характеристики, но текстового поиска нет. Выбранный тип ограничивает размеры
server-returned связью `typeDimensions` и очищает несовместимый размер до запроса. Карточка начинается
с номера без рамки, затем показывает тип тем же заголовочным размером; в ней нет предварительных
статуса доступности и срока доставки. Перелистывание/полноэкранные фото не ведут в паспорт.
Доступную складскую мебель можно назначать по бытовкам через «+ Дополнительно».

Карточки бытовок в каталоге и корзине показывают актуальную месячную цену logistics по типу и
категории бытовки из asset. Точные строки целых рублей читаются без округления, включая явный
нулевой тариф по умолчанию. Отсутствующая или некорректная цена — ошибка, а не бесплатная аренда.
Месячная аренда отделена от доставки и сборов; чтение каталога/корзины не фиксирует условия заказа.

Тип существующего профиля физлица/юрлица неизменяем, а имя/компания и контактные поля редактируются
под version fence профиля logistics. Круглая кнопка профиля показывает инициалы либо текущий
авторизованный аватар. Системный Android Photo Picker не требует разрешения на хранилище. Профиль
может подготовить точный subject-bound scope `LOGISTICS_CUSTOMER_PROFILE/PROFILE_AVATAR` до выбора
каталога: используется склад уже привязанного аватара, текущий склад каталога либо первый разрешённый
склад; сервер всё равно проверяет эту immutable scope. Приложение загружает и финализирует одно
изображение, ждёт его текущее поколение `READY` и привязывает к профилю. Владельцем байтов остаётся
media-service.

Корзина показывает каждую выбранную бытовку карточкой с собственным управлением сроком аренды,
листом дополнительной мебели/оборудования и удалением; checkbox-ов и массового срока аренды нет.
Полный набор сроков сохраняется через logistics-owned replacement endpoint. Изменение бытовки,
мебели или срока инвалидирует прежние слоты. Экран подтверждения использует
один и тот же срок по умолчанию «1 месяц» и для показанного значения, и для
доступности checkout, поэтому временно отсутствующая локальная запись срока не
блокирует корректный удержанный слот. Доставка разделена на четыре шага
Navigation 3: полноэкранная карта/адрес Яндекса, серверные даты, точные
возвращённые фиксированные или дневные слоты, затем проверка сроков по бытовкам и checkout. Каждый
слот содержит обязательный `kind`: для `FIXED_WINDOW` показывается точный интервал, а для
`DURING_DAY` в превью даты, выборе слота и подтверждении показывается «В течение дня. Точное время
подтвердит логист», при этом ненулевые серверные границы не скрываются из transport. В течение дня
всегда идёт последним в пределах даты, включая перенос доставки; фиксированные окна упорядочены по времени.

Карта использует поддерживающий стили `MapType.VECTOR_MAP` в плоском режиме 2D на logistics-owned depot, удерживает pan/pinch в MapKit и показывает плюс, минус и
нижнюю правую стрелку текущего местоположения. Точка из касания, подсказки или устройства сразу
показывается синим bitmap-маркером с кубом. Голубая палитра и night mode следуют явной светлой/тёмной
теме приложения. Общая шапка и стеклянные контролы используют ту же палитру; контролы карты скрыты
при открытой клавиатуре. Обязательная подпись Яндекса находится слева снизу над измеренной панелью
адреса и позиционируется через SDK API alignment/padding. Только нажатие на стрелку запрашивает у Android приблизительное/точное
местоположение; отменяемые одноразовые запросы Android соревнуют только включённые GPS, network и
passive providers, центрируют маркер и обратно геокодируют ту же связку адреса/точки. Отказ,
выключенные providers, timeout и отсутствие результата показаны явно.
Переключателя слоёв нет; спутниковый и гибридный слои не запрашиваются. Нижняя панель содержит
только поиск адреса, голосовой ввод Яндекс/Алисы, статус и стрелку продолжения, закреплена над IME и
не перетаскивается. Во время ввода появляются живые подсказки Яндекса. Выбор подсказки, отправка
набранного текста, касание карты либо текущее местоположение ставят маркер и разрешают точную
связку адреса/точки без лишней надписи о подтверждении. Русская речь принимается только из
установленной activity распознавателя Яндекса;
подписей/ручного ввода координат нет, как и fallback на Google либо
произвольный системный распознаватель. Если голосового ввода Яндекса нет,
приложение показывает модальное окно «Установить голосовой ввод». Изменение адреса или точки инвалидирует
связку, подтверждения доступа и слоты.

Нажатие «Продолжить» при подтверждённых адресе/точке и непустой серверной корзине сначала открывает
модальное окно про вместимость объекта, проезд машины по частной территории и ответственность за
холостой выезд. Для одной выбранной бытовки ёмкость фиксируется как `1` и машина без прицепа; для
двух и более бытовок показаны два равных варианта `1`/`2`, где `2` означает машину с прицепом. Изменение
ёмкости инвалидирует прежние offers, hold и подтверждения. Оба checkbox обязательны до отправки
запроса слотов, а та же ёмкость повторно фиксируется при hold. Переход к датам происходит только после успешного завершения
нового server search generation; ошибка не открывает пустой экран. Во время
запроса недоступный для закрытия overlay блокирует повторные действия и
показывает spinner над `Идёт расчёт свободных слотов`; при успехе или ошибке он
исчезает. Последующий hold повторно проверяет те же два зафиксированных факта вместе с ёмкостью и
отклоняет устаревший либо неполный offer. Изменение любого ответа сохраняет полученные предложения и
выбранный слот, но очищает существующий hold.
Logistics, а не APK, проверяет дороги для зафиксированного профиля высоты,
ширины, длины, массы и осей и возвращает профиль со слотами. На шаге даты серверная цена показана
после заголовка и пояснения. Изохроны и полигоны особой цены остаются метаданными transport и не
показываются клиенту. Отсутствующий или противоречивый тариф показывается как `Не рассчитана` и не заменяется локальным нулём. Известные
цены в целых рублях группируются по locale из серверного integer без floating-point и локального
расчёта цены. Запретные
и запрещающие прицеп полигоны остаются серверными ограничениями маршрута; APK не считает источник цены
признаком выполнимости. Даты
и слоты строятся только из точных серверных предложений. Вариант `DURING_DAY` всё равно удерживается
и повторно проверяется logistics перед checkout; APK не выбирает час прибытия.

«Мои заказы» раскрывает бронирования до бытовок. Приёмка доступна только после
COMPLETED у точного shipment driver task; клиент расписывается на полноэкранном
ограниченном векторном canvas и принимает бытовки отдельно. Для прибывшей
бытовки можно сообщить проблему до или после приёмки с категорией и описанием.
CameraX последовательно снимает фото и silent MP4-видео в app-private cache без
системного подтверждения; document picker импортирует поддерживаемые фото/видео,
а мини-галерея позволяет удалить файл. Доказательства загружаются в точную
строку `LOGISTICS_SHIPMENT`, финализируются, ожидаются до `READY` и только затем
входят в immutable problem command.
Повторы приёмки и сообщения о проблеме используют durable request identity после смерти процесса;
неопределённый ответ сверяется с авторитетным бронированием до очистки локального recovery state.
«Мои заказы» также поддерживает отмену и перенос доставки, принадлежащие сервису, только для
идентифицированного бронирования `COMPLETED`. Обе команды передают точную версию бронирования;
отмена и атомарная замена слота дополнительно используют переживающий смерть процесса
`Idempotency-Key`. Варианты замены ищутся только для этого бронирования, а подтверждение передаёт
ID/версию выбранного серверного слота и обязательные ID/версию котировки изменения, но не исходные
payload корзины, бытовок или мебели. До применения приложение показывает серверную котировку:
неустойку в точных целых рублях (строка в транспорте) и снимок новой даты/окна. Тестовая оплата —
явное согласие в той же команде; только точный GET котировки с `TEST_PAID`/`APPLIED` показывает
нефинансовую тестовую отметку без второго подтверждения. `APPLYING` разрешает проверку статуса,
но не повторную оплату. После смерти процесса сохраняются только ID котировки/бронирования и
fingerprint повтора, никогда деньги или статус оплаты. Действующий перенос, включая освобождение
менеджером от неустойки, восстанавливается по котировке без выдуманного слота. Просроченные или
не настроенные предложенные условия можно пересчитать; просроченное освобождение сохраняется
с предложением связаться с менеджером, а не заменяется платными условиями. Переданный сервером
телефон открывает Android `ACTION_DIAL`, не автоматический звонок; отсутствие номера или dialer
показывается явно. Ответ команды сверяется с авторитетным списком бронирований, поэтому
неудачная замена сохраняет прежнее представление доставки. `CANCELLATION_PENDING` и `CANCELLED`
имеют русские клиентские подписи, стабильные domain codes преобразуются в понятные русские
сообщения, а отсутствующий `cancellationFeeRubles` не отображается как ноль. Транспорт и recovery
реализованы в
[`CustomerApi.kt`](app/src/main/java/dev/buhanzaz/rwms/client/data/CustomerApi.kt) и
[`CustomerRepository.kt`](app/src/main/java/dev/buhanzaz/rwms/client/data/CustomerRepository.kt),
presentation policy — в
[`CustomerPolicies.kt`](app/src/main/java/dev/buhanzaz/rwms/client/ui/CustomerPolicies.kt).

На всех размерах окна навигация находится в боковом меню с логотипом BLOCK BOX. В каталоге, заказах и
профиле справа снизу появляется кнопка корзины с ненулевым числом выбранных бытовок. В корзине и потоке
доставки эта кнопка скрыта. Переходы вперёд, назад и системный жест возврата настроены явно; возврат из
профиля восстанавливает предыдущий экран. Полноразмерный drawer содержит один переключатель светлой/тёмной
темы; системная тема и режим по заряду не поддерживаются. Экраны и полноэкранные dialog edge-to-edge и
IME-aware. Клиентские команды сериализуются, 409 перечитывает авторитетную
корзину, checkout сверяется с долговечным списком бронирований.

## Граф зависимостей

Hilt предоставляет один application graph. Retrofit с Kotlin serialization
владеет типизированным API transport; OkHttp — Bearer/refresh обработкой; Coil
загружает изображения; Media3 — единым lifecycle-aware беззвучным фоновым циклом;
Yandex MapKit `4.42.0-full` — картой, подсказками, прямым и обратным
геокодированием; Android `LocationManager` — отменяемым foreground-получением текущей точки;
CameraX — встроенной сессией
фото/silent-video. Установленная
activity распознавания Яндекса владеет необязательным русским голосовым вводом,
поэтому CustomerApp не запрашивает разрешение микрофона и не хранит аудио. Разрешения
местоположения запрашиваются только по явной стрелке карты и не включают фоновый доступ. APK
не содержит cloud SpeechKit credential: для гарантированного server-side
распознавания Алисы нужны отдельно одобренные учётные данные Yandex Cloud и
server proxy; сервисный секрет нельзя встраивать в APK. UI
policy-объекты остаются чистыми и покрыты unit-тестами. Приложение отправляет подтверждённые адрес,
координаты и заявленную клиентом ёмкость одного заезда (`1` без прицепа или `2` с прицепом); профиль
и заказанное число бытовок logistics читает из авторитетной клиентской сессии и корзины.

## Сборка и проверка

Используйте Gradle 9.1 и JDK 17. На VPS ограничивайте сборку:

    ./gradlew testDebugUnitTest assembleDebug \
      --no-daemon --max-workers=2 \
      -Pkotlin.compiler.execution.strategy=in-process

Для каждой сборки нужен доступный только root файл properties вне репозитория:

    mapkitApiKey=<ключ Yandex MapKit>

Нестандартный путь передаётся через
`-PmapkitPropertiesFile=/protected/path/mapkit.properties`. Ключ попадает в
приложение только через сгенерированный `BuildConfig`; его нельзя коммитить или
печатать в build-логах. Поскольку клиентский SDK-ключ неизбежно присутствует в
APK, ограничьте его в кабинете Яндекса точным application ID и сертификатом
release-подписи.

Release APK намеренно включает только Android ARM ABI `arm64-v8a` и
`armeabi-v7a`. Debug APK дополнительно включает `x86_64`, поэтому его можно
устанавливать в Google APIs x86_64 AVD с API 30 или новее; 32-битный `x86`
остаётся исключённым. Для аппаратного ускорения такого AVD в Linux нужны
видимый гостевой системе CPU-флаг `vmx` или `svm` и `/dev/kvm`. Если сам VPS
работает поверх KVM, провайдер всё равно должен разрешить nested virtualization;
без неё эмулятор работает в медленном программном режиме.

Debug-артефакт — `app/build/outputs/apk/debug/app-debug.apk`, пакет —
`dev.buhanzaz.rwms.client.debug`. Для production-публикации передаётся внешний
доступный только root `signingPropertiesFile` и собирается `assembleRelease`;
keystore и пароли никогда не попадают в репозиторий. Проверенный release APK
обновляет только `client-download-site/`. Каждая release-задача создания
артефакта до выполнения проверяет четыре обязательных signing properties и
указанный keystore; названия полей приведены в
[`signing.properties.example`](signing.properties.example). Download-site затем
независимо требует package identity канала `PRODUCTION`, неизменяемый hash APK,
происхождение source и сертификат, закреплённый в
`client-download-site/release-trust-policy.json`.
