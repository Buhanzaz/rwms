# RWMS CustomerApp

CustomerApp — нативное Android-приложение клиента для бронирования бытовок.
Application ID — `dev.buhanzaz.rwms.client`, минимальная ОС — Android 11
(API 30), compile/target SDK — 36. Приложение независимо от ManagerApp и
WorkerApp.

English version: [README.md](README.md).

## Владение и границы

Приложение обращается только к публичному gateway из
`RWMS_PUBLIC_BASE_URL`. Для аутентификации используются `/auth/**`, для аренды
клиента — `/api/logistics/customer/v1/**`. Серверные данные остаются
авторитетными: приложение локально не создаёт доступность бытовок, остатки
мебели, слоты доставки или успешное бронирование.

## Аутентификация

Вход выполняет OAuth 2.0 Authorization Code с S256 PKCE для клиента
`rwms-customer-android`. Логин/пароль и cookies Spring-сессии существуют только
во время одного native-обмена и никогда не сохраняются. Callback
`https://localhost/auth/customer/callback` разбирается и проверяется внутри
процесса, а не открывается. Регистрация сначала получает CSRF metadata,
отправляет подтверждённый пароль, затем запускает тот же PKCE-вход.

Access/refresh token сохраняются в DataStore как AES-GCM ciphertext. Ключ —
неэкспортируемый материал Android Keystore. Отклонённый access token
обновляется один раз; повторный 401 завершает сессию, а при 409 приложение
перечитывает авторитетную корзину и инвалидирует устаревшие данные слота
доставки. Отдельный неавторитетный указатель DataStore хранит только ID
выбранного склада, ID inquiry и стабильный idempotency key создания inquiry.
Он очищается при выходе и позволяет после пересоздания процесса повторить или
перечитать inquiry до загрузки авторитетной корзины.
Повтор в том же процессе после неопределённого ответа создания использует этот
незавершённый ключ, а не открывает другую inquiry.

## Клиентский поток

Jetpack Compose Material 3 и Navigation 3 дают взаимоисключающие signed-out и
signed-in графы. Signed-in поток собирает профиль физлица или юрлица, выбирает
склад, постранично загружает все возвращённые сервером свободные бытовки по
одной карточке в строке и фильтрует их по типу, отделке, размеру, категории,
линолеуму и характеристикам. Поток поддерживает перелистывание/полноэкранные
фото без маршрута в паспорт, резервирует доступную мебель по бытовкам,
показывает корзину и оформляет долговечное бронирование. Доставка разделена на
четыре сфокусированных шага Navigation 3: полноэкранная карта и адрес,
возвращённые сервером даты, точные серверные слоты, затем срок аренды и
подтверждение. Изменение бытовок или мебели сбрасывает прежний выбор слота и
требует нового серверного расчёта ёмкости.
Ответ склада несёт координаты логистического депо. Карта доставки открывается
на этом депо полноэкранной векторной картой Яндекса, удерживает pan/pinch-жесты
внутри MapKit и предоставляет кнопки разрешённых векторного/растрового слоёв,
плюс, минус и возврата к выбранной точке. Спутниковый и гибридный типы Яндекс
разрешает только приложениям Яндекса, поэтому CustomerApp их не использует;
маршруты, пробки и погода также не включаются. Нижняя поисковая панель принимает
введённый адрес, точное касание карты, ручной резервный ввод
адреса/координат или русскую речь из системного распознавателя Android.
Распознанный текст проходит то же геокодирование Яндекса и не обходит
подтверждение адреса/точки. Стрелка продолжения недоступна, пока адрес,
координаты и непустая серверная корзина не валидны совместно. Следующий экран
дат группирует только точные возвращённые предложения и не создаёт локальную
доступность календаря. Завершившийся пустой поиск слотов показывается как
отсутствие доступного времени, а не как предложение повторить тот же запрос.
После успешного создания inquiry выбранный склад и inquiry ID становятся
активным workflow до запросов facets и первой страницы каталога. Поэтому более
поздняя ошибка зависимости каталога оставляет приложение на экране каталога и
не превращает повторное нажатие на склад в создание ещё одной inquiry.
Клиентские команды сериализуются без постановки повторных жестов в очередь.
Статус checkout сверяется с более новым долговечным списком бронирований:
отклонённое оформление удаляет уже освобождённый слот, а состояния pending и
completed блокируют последующие изменения корзины.

На телефоне используется нижняя навигация, в больших окнах — navigation rail;
сфокусированный поток доставки скрывает обе. Все экраны edge-to-edge, учитывают
IME и содержат content description для интерактивных иконок/фото. Yandex MapKit
Full изолирован в адаптере карты доставки. Введённый или распознанный голосом
адрес геокодируется рядом с выбранным депо; касание карты сохраняет точные
координаты касания и выполняет обратное геокодирование адреса. Редактирование
адреса или ручного черновика координат инвалидирует прежнюю связку и очищает
устаревшие слоты. Явное ручное подтверждение адреса/широты/долготы остаётся
резервным путём. Поиск слотов доступен только после совместного подтверждения
адреса и точки и при наличии бытовки в серверной корзине.

## Граф зависимостей

Hilt предоставляет один application graph. Retrofit с Kotlin serialization
владеет типизированным API transport; OkHttp — Bearer/refresh обработкой; Coil
загружает изображения; Yandex MapKit `4.42.0-full` — картой, прямым и обратным
геокодированием. Activity системного распознавания Android владеет
необязательным русским голосовым вводом, поэтому CustomerApp не запрашивает
разрешение микрофона и не хранит аудио. Это не гарантированная интеграция с
Яндекс Алисой/SpeechKit: для неё нужны отдельно одобренные учётные данные
Yandex Cloud и серверный proxy; сервисный секрет нельзя встраивать в APK. UI
policy-объекты остаются чистыми и покрыты unit-тестами. Приложение отправляет
только подтверждённые адрес и координаты; профиль и число бытовок logistics
читает из авторитетной клиентской сессии и корзины.

## Сборка и проверка

Используйте Gradle 9.1 и JDK 17. На VPS ограничивайте сборку:

    ./gradlew testDebugUnitTest assembleDebug \
      --no-daemon --max-workers=2 \
      -Pkotlin.compiler.execution.strategy=in-process

Для каждой сборки нужен доступный только root файл properties вне репозитория:

    mapkitApiKey=<ключ Yandex MapKit>

Нестандартный путь передаётся через
`-PmapkitPropertiesFile=/protected/path/mapkit.properties`. Ключ попадает в
приложение только через сгенерированный `BuildConfig`; его нельзя коммитить или
печатать в build-логах. Поскольку клиентский SDK-ключ неизбежно присутствует в
APK, ограничьте его в кабинете Яндекса точным application ID и сертификатом
release-подписи.

Debug-артефакт — `app/build/outputs/apk/debug/app-debug.apk`, пакет —
`dev.buhanzaz.rwms.client.debug`. Для production-публикации передаётся внешний
доступный только root `signingPropertiesFile` и собирается `assembleRelease`;
keystore и пароли никогда не попадают в репозиторий. Проверенный release APK
обновляет только `client-download-site/`.
